# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Genshin Impact gacha wish calculator. Given your current pity/guarantee state on the Character and Weapon Event Wish banners plus a priority-ordered list of goals (5★/4★ characters and weapons, with optional constellation/refinement targets), it computes exact — not simulated — probabilities of completing each prefix of your goal list by every pull count up to your budget, plus a full constellation/refinement breakdown for every 4★ goal. Client-side only, no backend.

## Current status — read before starting new work (as of 2026-08-19)

**Both the weapon Epitomized Path bug and a related 4★-pool dilution bug are now FIXED — banner configs (`featured4StarIds`/`featured4WeaponIds`/`chosenWeaponId`/`otherFeaturedWeaponId`) are computed fresh PER PHASE** (`phases.ts`'s `computeCharacterBannerConfigForPhase`/`computeWeaponBannerConfigForPhase`), not once globally. See "Banner config is derived from goals, per phase" and "5★-weapon identity is scoped to its own phase" below for the mechanism. **But this surfaced a much bigger, previously-unmeasured problem that changes what's actually achievable**, found by directly profiling the fix rather than guessing at a safe cap:

`PersistentSpec` (`goalTracking.ts`) tracks every named 4★ goal for a banner in ONE joint vector across that banner's *entire* lifetime (needed for correctness — see its own doc comment). When a banner is reused in a later phase, a goal whose value FROZE after its own earlier phase graduated still rides along as a live dimension in that later phase's state space — and since that frozen value genuinely *varies* across the distribution reaching the later phase (not a point mass), the later phase's own reachable-state count multiplies by that variety, on top of whatever's newly varying there. This is far steeper than the "8x per character 4★, 6x per weapon 4★" the existing `MAX_FOUR_STAR_GOALS_PER_BANNER` cap's own doc comment already warned about — it's a genuine *combinatorial cross-phase compounding*, not just a bigger constant. **Directly measured** (not guessed) via `runExactSimulation` at this app's default 90-pull budget: 3 character 4★s split 2-then-1 across two phases took ~39s (comparable to the existing single-phase 3-goal cost, ~29s — itself apparently never actually measured before, since the original performance work's own documented worst case only tested 2 goals); a 4th (2+2 split) took **12 seconds at a pull budget of just 20** and did not complete within several minutes at the real 90-pull default. Weapon (gentler `maxCopies` dimension — 6 vs. character's 8) tolerated a 2+2 split (4 total) at ~44s, but wasn't pushed further. **(These specific numbers are the PRE-optimization baseline that motivated the cap decision below — a second optimization pass the same day found real, unclaimed headroom in the DP engine itself, dropping the single-phase N=3 case to ~11s and the 2+2-split case to a measured 120s at pullBudget=90 (down from "didn't finish in several minutes") — see "`runPhaseDp`'s state is organized into slices"'s "Second optimization pass" below for the full numbers. This is a pure constant-factor win and does NOT change the cap conclusion — 120s is still far too slow to allow — but it's worth knowing the cap wasn't chosen against today's slowest-possible numbers.)**

**Consequence: the total-per-banner cap could NOT be raised anywhere near the ~9 originally hoped for** (enough to comfortably track 4★s across 2-3 phases) — it's now `MAX_TOTAL_FOUR_STAR_GOALS_PER_BANNER` in `goalValidation.ts`, split from the real per-phase roster cap (`MAX_ACTIVE_FOUR_STAR_GOALS_PER_PHASE` = 3 character / 5 weapon, unchanged, still correctness-motivated), and set to **3 for character** (identical to the per-phase cap — meaning this fix's real, honest benefit for character is letting an existing budget of 3 be freely *distributed* across phases instead of forced into one, not letting you track more) and **4 for weapon** (one measured, tested increment above the old uniform-3 cap). Raising either further needs a real profiling pass first, and likely needs a deeper architectural fix (making `PersistentSpec`'s dimensionality itself phase-scoped, not banner-wide) rather than just a bigger constant, given how steep this cost curve is — that's a substantially bigger project than today's fix, not attempted. ## Architecture

For "given this goal list, what does the engine assume a player actually does, pull by
pull" — i.e. exactly when banner focus switches, when a 4★'s accrual window opens and
closes, and why — see [FOCUS_RULES.md](FOCUS_RULES.md). It's organized as a lookup
reference (worked examples, a quick-reference table of "what changes what"), companion
to the prose explanations below of *why* the code is shaped this way. Cross-validation
against Monte Carlo (`exactEngine.test.ts`) only proves the exact engine and `simulate.ts`
*agree* — it can't catch a conceptual error shared by both, since they were written
against the same understanding of these rules. `invariants.test.ts` targets exactly that
blind spot instead, checking logical relationships (e.g. "a wider anchor window can only
help, never hurt") between two runs of the exact engine alone, with no second
implementation to (mis)agree with.

### Engine is pure TS, independent of React

Everything under `src/engine/` has no React/DOM dependency and is unit-tested directly. `src/state/` and `src/components/` are the UI layer that consumes it. `src/engine/worker.ts` runs the engine in a Web Worker; `src/state/useSimulation.ts` is the debounced hook that talks to it.

### The live engine is exact, not Monte Carlo

`exactEngine.ts` (`runExactSimulation`) is what the app actually calls. It computes exact probability distributions via dynamic programming — no sampling, no trial count, no noise. `simulate.ts` (`runSimulation`) is a Monte Carlo implementation of the *same* mechanics, kept only as an independent cross-validation tool for tests (see `exactEngine.test.ts`) — it is not called from the shipped app or the worker. When you change goal-matching or tracking semantics, mirror the change in both engines or the tests will (correctly) disagree.

### Phase decomposition is the core algorithmic idea

A naive joint DP over both banners' full state spaces simultaneously is intractable (their product is tens of millions of states). `exactEngine.ts` instead:

1. Groups the priority-ordered goal list into **phases** (`phases.ts`) — maximal runs of consecutive same-banner goals. Banner focus only ever changes at a phase boundary, because focus is defined as "the banner of the highest-priority incomplete goal," which only depends on the fixed priority order, not on completion timing.
2. Runs each phase's own compact DP (`phaseDp.ts`) — banner pity/CR/fate state × a phase-local counter × a **persistent** goal-tracking vector (see below). Goals sharing a phase's banner are checked opportunistically on every pull, not sequentially by priority.
3. Stitches phases together by convolving each phase's own completion-time distribution with the accumulated arrival-time distribution from every phase before it (`cumulativeToDensity` + `convolve` in `exactEngine.ts`), so results land correctly on the *global* pull axis even though each phase's internal DP only knows its own local pull count.
4. When the same banner reoccurs in a later, non-adjacent phase (e.g. character → weapon → character), that later phase's starting state distribution is the earlier phase's exit-state distribution, normalized — not the user's raw input state. This carries over BOTH the banner's own pity/CR/fate substate and the persistent tracking vector (see below) — not just the former.

### `runPhaseDp`'s state is organized into "slices," not one flat map (performance)

Within one phase's own DP, a pull's effect factors into two genuinely independent pieces: which banner substate (`bannerCode` — pity/CR/fate) you land in, driven purely by `transitionCharacterBanner`/`transitionWeaponBanner`; and what happens to the goal-tracking vectors (`persistentCode`/`phaseCode`), driven purely by `updateGoalTracking`/`isGoalDone`/`isPhaseFullyDone` and the anchor-gating helpers — and critically, the goal-tracking side depends on *which outcome shape occurred* (rarity + kind + itemId), never on the specific `bannerCode` that produced it. `phaseDp.ts` exploits this: state is grouped into "slices," one per distinct `(persistentCode, phaseCode)` pair reached, each holding a dense `Float64Array` of probability mass indexed by `bannerCode` (confirmed via profiling to be dense enough — double-digit percentages of the full banner-substate space by the end of a typical run — that a flat array beats a sparse `Map`, both for lookup and iteration). Per pull, per slice: the goal-tracking result is computed **once per outcome shape** (a fixed, small set — `enumerateOutcomeShapes`, derived directly from the banner config) instead of once per `(bannerCode, slice)` pair, then applied to every banner substate in that slice via `getTransitions`'s already-cached per-`bannerCode` transition table as pure array arithmetic — no decode/encode/function-call in the innermost loop at all. This cut the documented worst-case scenario from ~22-25s to ~4.5s, verified byte-identical against the full test suite before and after (a restructuring of *how* the math is computed, not the math itself). Memory stays bounded because slices are only allocated for `(persistentCode, phaseCode)` pairs actually reached, not the full theoretical cross product — which is also why `goalValidation.ts`'s `MAX_TOTAL_FOUR_STAR_GOALS_PER_BANNER` matters: each additional 4★ goal tracked on a banner multiplies `persistentModulus` (and therefore the worst-case slice count) by 8x (character, C0-C6) or 6x (weapon, R1-R5) — and, as of 2026-08-18's profiling (see "Current status"), that multiplication compounds far worse than this simple per-goal reading suggests once a banner is reused across phases, which is why that constant stayed small rather than being raised to match this app's original ~9-goal ambition.

**Second optimization pass (2026-08-18, same day, after the 4★-pool-dilution profiling above surfaced how slow even the already-shipped N=3 case actually was — ~28.9s at pullBudget=90, never directly measured before).** CPU-profiled (`node --cpu-prof` against the DP directly, via vitest's worker thread) rather than guessed, and found the slice restructuring above — while it eliminated the *goal-tracking re-derivation* redundancy — left three remaining costs in the exact same innermost per-`(bannerCode, transition)` loop, now dominant once that first redundancy was gone:
1. `perOutcome` was a `Map<string, SliceOutcomeResult>`, looked up by a *string* `outcomeKey` on every single `(bannerCode, transition)` pair (tens of thousands of times per slice per pull) — profiled at ~28.6% of runtime. **Fixed**: `perOutcome` is now a plain array indexed by a precomputed integer `outcomeIndex` (each `CachedTransition` carries its own, resolved once when the transition cache is populated) — a direct array index instead of a string hash lookup.
2. `SliceMap`'s `totalMass: Map<number, number>` was updated eagerly on *every* `add()` call (a `Map.get`+`set` pair per elementary transition) even though it's only ever *read* a handful of times per slice per pull (in `reportActive`/`flushGraduatedLevelCounts`). **Fixed**: removed the field entirely; total mass is now computed lazily via a tight `sumMass()` reduction over the (already cache-resident) `Float64Array`, called only where actually needed.
3. `getTransitions`'s memoization cache was a `Map<number, CachedTransition[]>` keyed by `bannerCode` — a *bounded integer* (0..`bannerModulus`-1) — looked up once per active `bannerCode` per slice per pull. **Fixed**: switched to a plain array indexed directly by `bannerCode`, avoiding hash overhead entirely.
4. A smaller, related fix: the "not done" branch of `SliceOutcomeResult` now carries a direct reference to its destination slice's array (`destArray`, resolved once per outcome per slice via `SliceMap.getOrCreateArray`, since the destination slice never varies with `bannerCode`) — so the innermost loop writes `pre.destArray[t.nextBannerCode] += branchProb` directly instead of calling `SliceMap.add()` (a `Map.get` per call) tens of thousands of times.

**Measured result** (same methodology as the first pass — `runExactSimulation` timed directly, full test suite for correctness before/after each step): the *already-shipped* N=3-single-phase case dropped from ~28.9s to **~11.0s** (2.6x); the original documented worst-case scenario (2 four-stars, different same-phase anchors) dropped from the first pass's ~4.5s to **~1.7s** (a further 2.6x on top of the first pass's own win, ~13x combined from the pre-first-pass baseline). This is a pure constant-factor win — it does **not** change the total-cap conclusion above: the previously-hanging 2+2-split-across-phases case (4 total character 4★s) went from "did not complete in several minutes" to a *measured, finite* **120s** at pullBudget=90 — still far too slow to allow, confirming the cross-phase compounding is a real combinatorial (not just implementation-inefficiency) problem that no amount of constant-factor optimization on this same algorithm will fix. Worth reaching for the same profiling methodology (`node --cpu-prof` via `node .../vitest.mjs run <test> --pool=threads`, since `--pool=forks`' child process doesn't reliably inherit `NODE_OPTIONS` the way `--pool=threads`' same-process worker thread does) before assuming there's no more headroom in a slow scenario — there was real, unclaimed headroom here that a full session of prior performance work hadn't found, simply because nobody had profiled *this specific* already-shipped scenario before.

### Goal tracking is split into phase-local vs. persistent state (`goalTracking.ts`)

There are two separate tracking vectors, for two genuinely different lifetimes:

- **Phase-local** (`PhaseLocalSpec`, resets every phase): the shared FIFO counter (0..count) for THIS phase's own `5star_character` goals — matching over the character banner is deliberately identity-agnostic (see below), so wins are claimed FIFO by priority order. This resets because a `5star_character` goal genuinely represents a *separate, later* win once the current phase's own goals are exhausted (see below), not something that can still be claimed once we've moved on.
- **Persistent** (`PersistentSpec`, carries across *every* phase of a banner, built once from the *whole* goal list, not just one phase's goals): `5star_weapon` identity flags (chosen vs. other featured) and `4star_character`/`4star_weapon` copy counts (0-7 / 0-5, i.e. C0-C6 / R1-R5). These persist because multiple 4-stars (and both featured weapons) genuinely coexist on a banner and can be opportunistically obtained on *any* pull of that banner, regardless of which phase a goal's own priority slot happens to land in — e.g. a 4-star goal listed after a weapon-banner detour can still pick up copies during the character-banner pulls that happened *before* that detour. An earlier version scoped 4-star tracking to a goal's own phase only, which silently discarded any copies gained in an earlier phase of the same banner.

`updateGoalTracking` is where a pull outcome mutates both vectors; `isGoalDone` is where a goal's completion is derived from them. Both `phaseDp.ts` and `simulate.ts`'s bitmask-based Monte Carlo loop implement matching semantics against this same logic independently — `simulate.ts` mirrors the persistent/phase-local split by precomputing each goal's phase index and looking up the current phase's closed-goal set on every pull, rather than resetting anything.

### Why 5★ character goals ignore identity

`characterBanner.ts`'s config only tracks one currently-featured 5★ id. A second `5star_character` goal doesn't name a different character — it represents "whoever's featured on a future rerun." So matching for this kind checks only rarity+featured, not itemId, and the *earliest pending* such goal claims each featured win (see the comment on `goalMatchesOutcome`/`applyOutcome` in `simulate.ts` and the parallel logic in `goalTracking.ts`). 4★ and weapon goals, by contrast, are identity-specific, because multiple named options genuinely coexist on one banner at once.

**A `5star_character` claim in `simulate.ts` needs its own phase-boundary gate — FIXED 2026-08-18, found by the user reviewing the trace survey.** The identity-agnostic FIFO claim loop above (`applyOutcome`) had no check at all that the CANDIDATE goal's own phase had actually been reached by the CURRENT pull — only that it was the earliest not-yet-done `5star_character` goal in priority order. Since a same-phase 4★ anchored to an earlier phase's 5★ correctly keeps the character banner "in play" well past that 5★'s own win (see the anchoring section below — this is intended), a featured win landing during that extended stretch — before an intervening weapon-banner detour had even started — could get credited to a LATER phase's own `5star_character` goal, whose real-world patch hadn't structurally begun yet. Confirmed via exact-vs-Monte-Carlo comparison this was a real ~30% overstatement, confined to `simulate.ts` (and therefore `trace.ts`, which reuses its `stepOnePull`) — the exact engine's `PhaseLocalSpec` is naturally immune, since each phase's own DP only ever tracks its own phase's `5star_character` goals, so it structurally cannot reach into a later phase's goal at all. Never affected the live app. Fixed by threading the current pull's own phase index into `applyOutcome` and requiring `phaseIndexByGoalId.get(goal.id) === currentPhaseIndex` before a `5star_character` goal is even considered a claim candidate. Regression test: `trace.test.ts`'s "twelfth reported bug".

**A separate, smaller residual discrepancy was found WHILE verifying the fix above — ROOT-CAUSED 2026-08-19, reversing the original suspicion.** `simulate.ts` and the exact engine disagree by roughly 10-30 standard errors (not sampling noise) on a goal's completion probability specifically in scenarios combining (a) a same-phase 4★ that extends how long a phase takes past its own 5★'s win, with (b) a LATER phase *of the same banner* whose own 5★-character completion depends on that extension (e.g. `Odette → Alyosha(anchored to Odette, several copies needed) → Homa(weapon detour) → Miko`). The original writeup here assumed the exact engine must be right (structurally immune to the twelfth bug) and left `simulate.ts` as the likely suspect — **that assumption was wrong.**

**Actual root cause, confirmed by direct instrumentation (not just cross-validation):** `crCounter` (the Capturing Radiance counter) is genuinely *correlated with how long a phase takes* whenever something (here, Alyosha's copy requirement) extends the phase past the point its own 5★ was won — the longer the extra chase, the more chances for a 50/50 loss to have nudged `crCounter` upward. Measured directly: stratifying phase0's exit by how many pulls it took, `crCounter=0` accounted for 87% of trials finishing by pull 30, but only 19% of trials finishing by pull 151-200 (75% sat at `crCounter=1` there instead). This is a REAL, large correlation, not noise. The exact engine's phase-to-phase handoff (`exactEngine.ts`'s `startDist` from a prior same-banner phase's `exitSubstateDist`) carries a state distribution that's **marginalized over arrival time** — correct for the arrival-time distribution itself (convolved separately via `arrivalDensity`), but it applies ONE averaged `crCounter` distribution uniformly regardless of when a given trial actually arrives. Since trials that also manage to fit the intervening weapon detour inside the pull budget skew toward *early*-finishing phase0 trials (which skew toward `crCounter=0`, i.e. worse pity standing), the exact engine ends up crediting those trials with a rosier, borrowed-from-the-late-finishers `crCounter` distribution — systematically overstating the later goal's odds. This is the SAME class of approximation the "Known remaining limitation" paragraph under "4★ breakdowns sum across every phase" already documents for 4★ copy counts — that paragraph's claim that "pity/CR/fate reset... so the trick is exact for them" turns out to only hold when nothing extends the phase past the point of reset; an anchored 4★ breaks that assumption for `crCounter` too. See that paragraph's own update, below, for the corrected general statement.

**Verified `simulate.ts` is the trustworthy one here, not the exact engine**, via: (1) `simulate.ts`'s own phase0 (Odette+Alyosha) exit-state distribution matches the exact engine's own phase0-only computation almost exactly (confirms phase0 itself is correct in both engines, unconditionally); (2) character-banner state is confirmed byte-identical at "phase0 exit" and "Homa's own completion" within every single trial checked (the weapon detour genuinely doesn't touch it, as expected); (3) `simulate.ts`'s own POST-handoff continuation, given whatever state a trial actually captured, is unbiased relative to an independent exact single-goal computation (`exactCharacterBannerCdf`) — confirming the bug isn't in how `simulate.ts` continues from a state, only in the exact engine's approximation of what states arrive when.

**Genuinely affects the live app**, not just `simulate.ts`/`trace.ts` — corrects the original "does not affect the live app's actual odds" claim. Any real goal list shaped like [5★, same-phase 4★ needing several copies anchored to it, different-banner or same-banner-reoccurring detour, LATER 5★ of the same banner] will show a real, visible (up to ~0.7 percentage points measured here, at the app's own 1-decimal rounding) overstatement in the exact-engine-powered odds chart itself.

**Deliberately left as a documented, known limitation, not fixed, per explicit user decision 2026-08-19** — a full fix is the same architectural shape as the already-deferred 4★-copy-count fix below (re-run the downstream phase separately per arrival-time/state bucket instead of from one time-marginalized distribution), not a quick patch. If picked up later, start from the isolation and root-cause already established here rather than re-deriving it — see `gacha_mechanics_audit_findings.md` for the full diagnostic trail (the crCounter-vs-exit-time stratification table in particular).

### 4★ goals: target level vs. anchoring (two distinct, easily-confused concepts)

- **`targetLevel`** (C0-C6 / R1-R5) controls *when a goal is considered done* for priority/banner-focus purposes — how many copies you're willing to wait for before moving to the next goal. The full C0-C6/R1-R5 breakdown is always computed and shown regardless of this setting.
- **`anchoredFiveStarGoalIds`** controls *how long the 4★ stays trackable at all*, independent of its own target. **Real structure this models** (confirmed against actual patch data, e.g. Genshin 4.5 — Phase 1 {Chiori, Itto} shared {Gorou, Dori, Yun Jin}; Phase 2 {Neuvillette, Kazuha} shared a different {Yanfei, Barbara, Xingqiu}, zero overlap): one Genshin **phase** (~3 weeks) runs TWO simultaneous 5★ character banners sharing the same 3 featured 4★ characters, plus ONE 5★ weapon banner featuring BOTH its 5★ weapons (Epitomized Path choice between them). A different phase has its own, generally different, roster for both. So: `4star_character` gets up to 2 anchors (one per simultaneous character banner it might be rate-up on, referencing `5star_character` goals); `4star_weapon` gets at most 1 (only one weapon banner runs per phase — referencing either of its two `5star_weapon` goals is enough to identify "this phase's weapon window").

  Since 4-star copy tracking is **persistent** across every phase of a banner (see above), closure has to be evaluated **per phase, statically** — `phases.ts`'s `computeClosedFourStarGoalIdsForPhase(phases, p, fourStarGoals)` returns, for one specific phase index `p`, which items are closed *in that phase*: `p` falls **outside the inclusive range** [earliest anchor's phase, latest anchor's phase]. That range has two distinct edges: `p` strictly AFTER every anchor (guaranteed already won by then, since a phase can't graduate without its own goals — including any anchor it contains — being satisfied), or `p` strictly BEFORE every anchor (none of them have happened yet, so the item structurally isn't in that phase's real-world rate-up pool at all). **The second edge was a real bug, found during the ground-truth audit** (seventh/eighth reported bugs): the original implementation only ever checked the first edge, so an item positioned in an *earlier* phase than all of its anchors — legal per `goalValidation.ts`'s ordering rule, which only forbids a *foreign* same-kind 5★ goal sandwiched between an item and its anchors, and says nothing about the item's own phase relative to them — accrued copies from pull 1 of that earlier phase, long before its anchor's phase could possibly start. `goalValidation.ts` now also rejects this configuration outright (an item's own phase must not come before its earliest anchor's phase) rather than silently computing a number that's either wrong or a permanent 0%. **The first edge, in turn, needed its own exception, found by the user testing in the dev server the same day** (ninth reported bug): an item's own NATAL PHASE — the phase it's actually a member of, i.e. required for that phase's own graduation — must never be closed by the "after every anchor" edge, even though it structurally falls after the anchor range whenever the item is listed after a same-list detour (e.g. `[Odette(char), Weapon(weapon), Alyosha(char, anchored=[Odette])]` — Alyosha's own phase is the *last* one, strictly after her only anchor). Closing it there meant that phase — which exists *only* to pull toward that item — could never graduate past whatever mass had already accrued opportunistically in an earlier phase, hard-ceiling the whole downstream chain the instant the intervening detour phase finished, no matter the pull budget. The "before every anchor" edge needs no equivalent exception: `goalValidation.ts`'s check above already rejects that configuration outright, so by the time a validated list reaches this function, an item's own phase falling outside the anchor range can only ever be on the *after* side. This is recomputed fresh for each phase a banner has, not once globally, because the *same* persistent item can be open in one phase and closed in another as focus moves through the goal list. Critically, this must be a **per-phase, static** decision, not a live per-pull check against "has the anchor been won yet": when an anchor shares the SAME phase as the 4★ (the common case — e.g. a 5★ goal, its anchored 4★, and another 5★ goal all back-to-back on the same banner), the window must stay open through the *whole* phase even after the anchor is won mid-phase, since that phase structurally can't graduate until the 4★ is also done — checking anchor status live would incorrectly freeze the copy count the instant the anchor dropped, which was a real bug found twice during earlier development (once as an outright freeze, once when a "live persistent boolean" check reintroduced the same problem through a different code path). `simulate.ts`'s Monte Carlo loop mirrors all of this exactly (it directly reuses `computeClosedFourStarGoalIdsForPhase`, so every fix to it applies to both engines automatically): it precomputes each phase's closed-goal set once (not per trial, since it's derived purely from the goal list) and looks up the *current* phase (via the phase containing whichever goal is presently driving banner focus) on every pull. `goalValidation.ts` enforces the required invariants: no *other* same-kind 5★ goal may sit between an item and its anchor(s) in priority order (that would mean the anchors can't actually be the same/adjacent phase pairing); an anchor is required once there's enough same-banner 5★ ambiguity to need disambiguating — 2+ `5star_character` goals anywhere (for `4star_character`), or 2+ *distinct* weapon-banner phases (for `4star_weapon` — a single phase can hold both `5star_weapon` goals, chosen + other-featured, without any ambiguity at all, since that's still just one window). The app withholds the whole results chart (rather than compute something misleading) while any goal fails validation — see `App.tsx`.

  Anchoring also has to gate the **next 5★-character claim itself**, not just 4★ copy accrual, whenever multiple 5★-character goals share one phase — `goalTracking.ts`'s `isNextFiveStarClaimBlocked`. Without this, "anchored to one banner" and "anchored to both" would be indistinguishable in the same-phase case: a featured win was previously claimed by whichever pending `5star_character` goal is next in FIFO order regardless of any 4★'s anchor status, so a 4★ anchored to only the *first* 5★ couldn't actually delay the *second* 5★ from being claimed — even though in the real game you can't reach the second banner until you're done pulling on the first. The rule: a pending 5★-character win is blocked from advancing the FIFO counter (treated as just another copy of the *current* 5★, not a new one) if some `4star_character` goal in this same phase is anchored *only* to already-claimed 5★(s) — not also to the upcoming one — and hasn't reached its own target yet. `simulate.ts` mirrors this with the equivalent bitmask check, scoped to 4★s in the *same phase* as the pending 5★ (goals from other phases are irrelevant here — their closure is already handled by `closedGoalIds`). 5★ weapons don't need this: their identity is resolved directly per pull (chosen vs. other-featured vs. standard), never FIFO-claimed, so there's no analogous same-phase ambiguity to worry about.

  **A same-phase anchor set must cover EVERY 5★ sharing that phase, not just some of them — enforced by `goalValidation.ts` since 2026-08-18.** Found reviewing the trace survey (below) from an actual-player point of view: a 4★ anchored to only ONE of two same-phase `5star_character` goals (e.g. Odette+Miko share a phase, Alyosha anchored to Odette only) doesn't correspond to any real configuration — since both of a phase's simultaneous character banners always feature the *identical* 3-slot 4★ roster (see the patch example above), there's no such thing as "rate-up on this phase's first banner but not its second." Before this fix, the engine would silently compute a real (if unintuitive) number for an input that can't actually happen in the game, gated only by a live "has FIFO focus reached this anchor's rank yet" check (`isFourStarWindowOpen`/`isFourStarWindowOpenInPhase`) that made partial same-phase anchoring *behave* differently from full anchoring — a distinction with no real-world referent. `goalValidation.ts` now rejects a 4★ whose anchors touch a phase without covering every 5★-character goal in that phase, and separately caps same-phase `5star_character` goals at 2 (only 2 simultaneous character banners run per real phase — needed so the coverage rule is always satisfiable within the existing 2-anchor max). Weapon needs no equivalent: `maxAnchors=1` there already means a weapon 4★ can only reference ONE of a phase's (at most 2) `5star_weapon` goals, which is fine because unlike character, only ONE weapon banner ever runs per phase (the two `5star_weapon` goals are the chosen/other-featured split of that *same* banner, not two different banners). The underlying gating logic (`isFourStarWindowOpen`/`isFourStarWindowOpenInPhase`) was left as-is — it still produces correct results for every configuration `goalValidation.ts` now allows — this was purely an input-validation fix, not an engine-math fix.

**Update, 2026-08-19 (sixteenth reported bug): "sharing a phase" is no longer inferred from priority-list adjacency at all** — see that section below for the full fix. `Goal.linkedCharacterGoalId` now makes it explicit; the same-phase cap of 2 described above is consequently enforced structurally by that field (a goal can declare at most one partner) rather than needing its own dedicated scan, and the coverage rule above is untouched — it still operates on whatever `buildPhases` decides is one phase, which now reflects the explicit link instead of bare adjacency.

### 5★-weapon identity is scoped to its own phase

`5star_weapon` goal tracking (chosen vs. other-featured) is identity-specific like 4★ tracking, but — unlike 4★s — needs **no user-specified anchor** to know its window: a `5star_weapon` goal is unambiguously tied to whichever single phase it's positioned in, since each phase runs exactly one weapon banner. **This was a real bug, found during the ground-truth audit** (eighth reported bug): `WeaponBannerConfig` (`chosenWeaponId`/`otherFeaturedWeaponId`) is one static object built once from the whole goal list (see "Banner config is derived from goals" below) and reused unchanged across every weapon-banner phase — and `goalTracking.ts`'s 5★-weapon branch had no phase gating at all, unlike the 4★ branch's `closedGoalIds`. So a *later*, unrelated weapon-banner phase's featured weapon was reachable as a real pull outcome — and got silently marked "done" — during an *earlier* weapon-banner phase, piggybacking on whatever pulls that earlier phase's own goal was making. Fixed by `phases.ts`'s `computeClosedFiveStarWeaponTargetIdsForPhase(phases, p, fiveStarWeaponGoals)`, which closes every `5star_weapon` target whose own goal isn't a member of phase `p` — always active, not opt-in, since (unlike 4★s) there's no legitimate "shared across two phases" case to preserve: each phase's weapon banner is its own independent window. Threaded through `goalTracking.ts`'s `updateGoalTracking` (new `closedFiveStarWeaponTargetIds` parameter), `phaseDp.ts`, and `exactEngine.ts` the same way `closedGoalIds` is; mirrored in `simulate.ts` for the same reason as everything else in this section — both engines must agree.

**A second, deeper bug in this same area was CONFIRMED and is now FIXED** (found 2026-08-18, see `gacha_mechanics_audit_findings.md` for the full narrative): the fix above made 5★-weapon *tracking* phase-scoped, but `WeaponBannerConfig` itself — specifically which identity is `chosenWeaponId` vs `otherFeaturedWeaponId` — was still that one static, global object, unchanged across every phase. Since `transitionWeaponBanner`'s Fate Point guarantee (`if (state.fatePoints === 1)`) always resolves to `config.chosenWeaponId`, whichever identity that globally was, a `5star_weapon` goal that wasn't the very first one in the whole priority list could never be the beneficiary of a Fate Point guarantee in *any* phase, including its own — silently understating its true odds. **Fixed** by `phases.ts`'s `computeWeaponBannerConfigForPhase(phases, p, allWeaponFourStarGoals)`, which reads `chosenWeaponId`/`otherFeaturedWeaponId` straight off phase `p`'s own `5star_weapon` goals (first = chosen, second = other, padded if fewer than 2) instead of the whole list's global priority order — threaded into `exactEngine.ts`'s phase loop and `simulate.ts`'s `TrialInfo` (`characterConfigByPhase`/`weaponConfigByPhase`, precomputed once like `closedGoalIdsByPhase`) the same way `closedGoalIds` already was.

**`featured4StarIds`/`featured4WeaponIds` (the 4★ rate-up pools) had this SAME global-not-per-phase structure, and — unlike the weapon identity bug above — this WAS confirmed to be a real (if previously unrecognized) bug too, once total tracked counts could exceed the real roster size**: `buildSimulationInput.ts` used to build one combined pool from every named 4★ goal across the *whole* list, reused for every phase. Getting a featured 4★ has the *identical* state effect (pity4→0, guaranteed4→false) no matter which slot it lands on — there's no Fate-Point-style mechanic where "which specific identity you got" changes what's guaranteed later — so a named 4★'s own odds were still exactly `1/poolSize`, correct, as long as `poolSize` stayed pinned at the real roster size (3 character / 5 weapon). The OLD validation cap (`MAX_FOUR_STAR_GOALS_PER_BANNER = 3`, applied globally) happened to keep `poolSize` correct by construction — but that was doing double duty as both a performance bound AND (silently) the only thing preventing dilution, which understated the cap's true importance. **Fixed** the same way as the weapon case: `phases.ts`'s `computeCharacterBannerConfigForPhase` builds each phase's pool from the *complement* of `computeClosedFourStarGoalIdsForPhase`'s output — i.e., exactly the named 4★s actually in play for that phase — so `poolSize` is correct per phase regardless of how many total 4★s are named elsewhere in the list. This is what makes it *safe*, not just convenient, for the total-per-banner cap to be a purely performance-driven number now instead of a correctness-pinned one (see "Current status" at the top of this file for why that number still had to stay small).

### Weapon banner was missing its own 75/25 pity guarantee entirely — thirteenth reported bug (2026-08-19)

**Found by:** the user diagnosing `E2` in the trace survey — two 5★ weapon goals sharing one phase, where a standard-weapon loss should have set up a guarantee that never visibly took effect. Confirmed against real Genshin mechanics (web search plus, on one specific point the sources disagreed on, the user's own detailed correction, which turned out to be exactly right).

**The bug:** `WeaponBannerState` only ever tracked `fatePoints: 0 | 1` — there was no separate representation of the weapon banner's *own* 75/25 pity mechanic (structurally parallel to the character banner's 50/50 `guaranteed5`): after a **standard** (off-banner) 5★ weapon, the *next* 5★ weapon is guaranteed to be one of the 2 event weapons, independent of and in addition to Epitomized Path. The old code conflated this into `fatePoints` — a standard pull granted a fate point (correct), and `fatePoints===1` unconditionally forced the next 5★ to be 100% the chosen weapon (also correct on its own) — but with no separate state, there was no way to represent "guaranteed featured, but not necessarily the chosen one," which is exactly what should be left over once a Fate Point *expires* at a phase boundary while the 75/25 guarantee (a pity mechanic, not Epitomized-Path-specific) does not.

**Confirmed mechanic, from real Genshin sources and the user's correction:**
- A 5★ weapon that isn't your chosen one — either the OTHER event weapon or a standard one — grants 1 Fate Point.
- Once `fatePoints === 1`, it **fully overrides**: the next 5★ weapon is 100% your chosen one, regardless of the 75/25 guarantee's own state (a Fate Point doesn't merely act *within* the 75/25 branch, it bypasses the split entirely).
- A standard pull *also*, independently, sets "next 5★ weapon guaranteed featured" (`guaranteed5` — a 50/50 between the two event weapons on its own, no specific one).
- **Within one phase this is invisible**, since the Fate Point a standard loss also grants already forces 100% chosen on the very next 5★ — the 75/25 guarantee never gets to act alone. It becomes observable **across a phase boundary**: Epitomized Path is a per-phase selection, so `fatePoints` resets to 0 for a new weapon-banner phase, but the 75/25 guarantee (a pity mechanic, like pity5/guaranteed4) carries over unchanged — so the new phase's first 5★ is a genuine 50/50 between *that phase's own* chosen/other identities, not a guarantee of a specific one.

**Fixed:**
- `WeaponBannerState` gained `guaranteed5: boolean` (see its own doc comment in `types.ts` for the full state-combination table). `stateCodec.ts`'s weapon encoding gained a matching digit (`WEAPON_BANNER_MODULUS` doubled).
- `weaponBanner.ts`'s `transitionWeaponBanner` rewritten around the priority `fatePoints===1` > `guaranteed5` > baseline 37.5/37.5/25 — see its own doc comment for the full combination table.
- **The per-phase Fate Point reset** (the piece with no natural home inside a single-pull transition function) lives at the phase-boundary layer in both engines: `exactEngine.ts`'s `resetWeaponFatePoints` decodes/zeroes/re-encodes the `fatePoints` component of a carried-over `exitSubstateDist` whenever a weapon-banner phase reoccurs (merging any resulting duplicate keys); `simulate.ts` mirrors it via `TrialInfo.isReoccurringWeaponPhase` plus a `maxPhaseIndexSeen` high-water-mark threaded through `stepOnePull` (a trial's phase sequence is monotonically non-decreasing, so "phaseIndex > high-water-mark" is exactly "first pull of a new phase") — resets `fatePoints` to 0 exactly once, on the first weapon pull of a reoccurring phase, never touching the very first (starting-state) use of the banner.
- `WeaponBannerForm.tsx` gained a "last 5★ weapon was standard" checkbox (mirrors the character form's implicit `guaranteed5`), alongside the existing "have 1 Fate Point" one.
- `trace.ts` gained `weaponAnnotation` (the weapon-side counterpart to `crAnnotation`) — every weapon-banner 5★ pull now shows which mechanism decided the outcome (fate point spent / guaranteed-featured 50/50 / natural 75/25 roll) plus the real `FP a→b` / `guaranteed-featured a→b` transition, at the user's explicit request.

Regression tests: `weaponBanner.test.ts` (the transition function's full state-combination table, unit-level), `exactEngine.test.ts`'s "thirteenth reported bug" describe block (a phase-0-exits-with-fatePoints=1 shape, cross-validated exact vs. Monte Carlo; plus a direct check that `guaranteed5` alone produces a 50/50, not 37.5/37.5/25, on a fresh banner use).

### Epitomized Path must retarget to a phase's second weapon once the first is claimed — fourteenth reported bug (2026-08-19)

**Found by:** the user re-examining `E2` after the thirteenth-bug fix landed — WeaponA and WeaponB share one phase, and even once WeaponA is claimed and "focus" correctly shows WeaponB, a Fate-Point-guaranteed 5★ still resolved to WeaponA. Confirmed via investigation that this is a DIFFERENT, narrower bug than the "opportunistically credit whichever weapon drops first" feature originally floated for this case: `goalMatchesOutcome`/`updateGoalTracking` already match a `5star_weapon` goal by `itemId` alone, with no dependence on `kind` (`'featured'` vs `'featured_other'`) or on priority/focus — so a natural roll landing on WeaponB while WeaponA is still nominally "chosen" was *already* credited correctly before this fix. The ONLY real gap: `phases.ts`'s `computeWeaponBannerConfigForPhase` assigns `chosenWeaponId`/`otherFeaturedWeaponId` **once, statically, for the whole phase** (first-listed `5star_weapon` goal = chosen) — a rational player, once their first weapon is theirs, immediately re-selects Epitomized Path to the second, but the engine modeled a player who never touches their selection again. This permanently denied the second weapon the "guaranteed within 2 five-star pulls" bound Fate Points otherwise provide — it could only ever be won via the organic 37.5%/50% roll. **No new goal-list syntax, `goalValidation.ts` rule, or UI was needed** — priority order within the existing "2 weapons, 1 phase" shape (already valid input) already expresses "retarget to the second once the first is done."

**Fixed:**
- `phases.ts`'s new `computeWeaponBannerConfigAfterFirstClaimedForPhase(phases, p, allWeaponFourStarGoals)` returns the phase's normal config with `chosenWeaponId`/`otherFeaturedWeaponId` swapped, or `undefined` when the phase doesn't have exactly 2 `5star_weapon` goals (every phase before this fix, and the overwhelming majority still) — real weapon banners never have more than 2 event weapons, so this is the only shape needing a swap at all.
- **Exact engine** (`phaseDp.ts`): `runPhaseDp` accepts an optional `weaponConfigAfterFirstClaimed` and, when given, builds a SECOND `BannerAdapter` from it and selects PER SLICE (not once for the whole phase run) which adapter to use for a given `bannerCode` lookup — based on whether that slice's own persistent vector already shows the phase's first weapon goal's `targetId` as obtained (read directly off `persistentVector`, already decoded once per slice per pull for goal-tracking, so the check is free). This was made possible by generalizing `outcomeKey()`'s canonicalization: rarity-5 featured/featured_other outcomes are now keyed by `itemId` ALONE, dropping `kind` — safe unconditionally (a character banner's one such slot, and a weapon banner's at most two, are already uniquely identified by itemId regardless of which kind label currently applies), and it's exactly what lets both adapters' transitions resolve into the SAME `outcomeKeyToIndex` space, so the precomputed per-slice goal-tracking result (`perOutcome`, the whole point of the earlier "slices" optimization) never needs to double or re-derive.
- **Monte Carlo** (`simulate.ts`): far simpler, since `stepOnePull` already re-derives everything fresh per pull from the current `bitmask`. `TrialInfo` gained `weaponConfigAfterFirstClaimedByPhase`/`firstWeaponGoalIndexByPhase`; `stepOnePull` picks the swapped config once that phase's first weapon goal's bit is set.
- `exactEngine.ts`'s phase loop computes and passes the swapped config alongside the normal one whenever a weapon phase has 2 `5star_weapon` goals.

**Verified against a precise, closed-form acceptance criterion** (not just cross-validation): seeded so WeaponA is claimed deterministically at pull 1 (`fatePoints=1` from the start), then confirmed `P(both done)` reaches exactly 1 at pull 161 — 1 (WeaponA) + 80 (WeaponB's own hard pity to bank a Fate Point, worst case) + 80 (the forced, guaranteed-chosen second cycle) — and is meaningfully below 1 well before that (e.g. ~10% at pull 80), ruling out both "retarget doesn't work at all" and "retarget is trivially free" as failure modes. Also cross-validated exact vs. Monte Carlo on the realistic fresh-state `E2` shape, and confirmed the existing single-weapon-per-phase tests (including the tenth-bug test) are completely unaffected — the guard (`weaponConfigAfterFirstClaimedByPhase[p] === undefined`) makes every phase but this specific shape take the exact same single-adapter path as before. Regression tests: `exactEngine.test.ts`'s "fourteenth reported bug" describe block.

**UPDATE, same day, immediately after the paragraph above was written — CORRECTED, was too narrow:** the claim that this fix already covers the full "chase both weapons" scenario is only true when the two `5star_weapon` goals are ADJACENT in priority order (nothing else between them). The user identified a direct counterexample: priority `[Odette, OdetteWeapon, Raiden, RaidenWeapon]`, where Odette and Raiden are the SAME real phase's two simultaneous character banners (per this file's own documented real structure — see "4★ goals: target level vs. anchoring" below), and OdetteWeapon/RaidenWeapon are that SAME phase's one shared weapon banner's two event weapons. Priority order here NATURALLY interleaves character and weapon goals from the SAME real-world window — but `buildPhases()` groups phases purely by "maximal adjacent run of the same `goal.banner`", so this list becomes 4 SEPARATE phases, and the weapon pair is treated as two unrelated windows: `computeWeaponBannerConfigForPhase` for OdetteWeapon's own phase doesn't even know RaidenWeapon exists (its "other" slot falls back to an anonymous placeholder, not RaidenWeapon's real `targetId`), and `computeClosedFiveStarWeaponTargetIdsForPhase`'s existing doc comment explicitly says *"there's no legitimate 'shared across two phases' case to preserve"* for `5star_weapon` — an assumption this exact scenario disproves. **The reverse also needs to be expressible**: `[WeaponA, WeaponB]` adjacent in priority today ALWAYS means "same window" — but the user also wants to be able to say two adjacent weapon goals are genuinely on DIFFERENT real phases (e.g., already own both characters, just need each phase's own weapon banner in sequence) with no opportunistic sharing between them.

**Conclusion: "same real weapon banner window" vs. "different windows" needs to be an EXPLICIT, user-specified relationship, decoupled from priority-list adjacency** — adjacency is neither necessary nor sufficient to express it. The natural analog is the existing 4★ `anchoredFiveStarGoalIds` mechanism (`types.ts`), which already solves a structurally similar problem (a 4-star's real availability window, decoupled from its own list position) — but `5star_weapon` goals currently have NO such field at all (their doc comment in `types.ts` explicitly says "needs NO user-specified anchor," which this finding shows is no longer true for the general case). This is a real, unimplemented feature needing its own dedicated planning pass (both engines' phase-loop/config-computation logic would need to key off something other than raw phase index for weapon config purposes) — **not started this session.** See `gacha_mechanics_audit_findings.md` for the full writeup and the concrete examples to design against.

### 5★-weapon window linking is explicit, not inferred from adjacency — fifteenth reported bug (2026-08-19)

**Implements the feature the fourteenth-bug fix's own follow-up section (above) identified but didn't start.** `Goal` gained `linkedWeaponGoalId?: string`, meaningful only on `5star_weapon` goals: points at the OTHER `5star_weapon` goal sharing this SAME real weapon-banner window (shared Epitomized Path pool, shared Fate Point progress, opportunistic crediting either direction). Symmetric (validated) — if A links to B, B must link back to A. **There is no adjacency-based default anymore, a deliberate behavior change**: absence means "different window" (even if adjacent in priority order), presence means "same window" (even if far apart, split by a character-banner detour). This directly fixes both of the fourteenth-bug follow-up's counterexamples:
1. `[Odette, OdetteWeapon, Raiden, RaidenWeapon]`, linked — Odette/Raiden's shared real phase's two character banners naturally interleave with that same phase's one shared weapon banner in priority order; the link is what lets RaidenWeapon opportunistically benefit from OdetteWeapon's own phase's pulls (and vice versa), even though they land in 4 separate `Phase` objects.
2. `[WeaponA, WeaponB]`, left unlinked — genuinely two different real phases (e.g. already own both characters) now correctly get NO sharing at all, where before adjacency alone always forced them into one shared window.

**Went through a full plan-mode pass, including a dedicated design-review sub-agent pass** (mirroring the fourteenth-bug fix's own process) that re-derived the two hardest claims from the actual code rather than trusting the prior session's own speculation:

### 5★-character window linking is explicit, not inferred from adjacency — sixteenth reported bug (2026-08-19)

**Found by:** the user hitting it directly in the live UI (not the trace survey this time) — a goal list `[Miko, 4starA(anchored to Miko only), Furina, 5star]` showed TWO validation errors: 4starA rejected for "anchored to only some of the 5★ character goals sharing this phase (missing Furina, 5star)", and the 4th 5★ goal rejected for "too many 5★ character goals share one phase." Root cause: `buildPhases` assumed EVERY adjacent run of `5star_character` goals was one shared (simultaneous) phase — exactly the fifteenth reported bug's mistake, but on the character side, and arguably worse there: it meant a goal list like this could never express "these are 4 SEQUENTIAL 5-stars from 4 different real phases," only ever "these all share one phase" (which then correctly gets rejected once there are 3+, since only 2 simultaneous character banners exist per real phase). Chasing 3+ 5-stars in a row with no weapon detour between them was structurally impossible before this fix.

**Fix, mirroring the fifteenth-bug's shape but NOT its semantics — the user was explicit about this distinction and it matters:** `Goal` gained `linkedCharacterGoalId?: string`, meaningful only on `5star_character` goals, symmetric, validated the same way as `linkedWeaponGoalId`. But "linked" here means SIMULTANEOUS, not "same banner" — two linked characters are two SEPARATE banners running at once (you cannot lose your 50/50 to "the other one," since there's no such shared roll), which merely share pity/guaranteed5/crCounter state and the 4★ roster (a real, confirmed Genshin mechanic: switching which of two simultaneous character banners you pull on does not reset your pity). Absence means "different, sequential phase" — no adjacency-based default anymore, matching the fifteenth-bug's own precedent.

**One genuine difference from the weapon fix, found by re-deriving rather than copy-pasting the pattern:** a linked character pair must have no OTHER `5star_character` goal between them in priority order — validated in `goalValidation.ts`. This isn't just a simplification — it's required by the mechanic itself: two banners that are genuinely simultaneous share ONE continuous real-world pull window, so a different, unrelated character banner prioritized between them wouldn't correspond to anything achievable in the actual game. Since `buildPhases`'s merge check is one-directional and a goal can only declare ONE partner, this also means (confirmed by direct derivation, not assumed) that 3+ `5star_character` goals can never end up sharing one phase anymore, through any input — the pre-existing "caps same-phase 5-star character goals at 2" validation rule in `goalValidation.ts` is consequently unreachable through normal input now, left in place as harmless defensive code (its own regression test was removed rather than force-fit into an unreachable shape — see `goalValidation.test.ts`).

**UPDATE, same day, found reviewing a real Odette/Raiden trace scenario (`trace.survey.test.ts`'s `E6`) — the ORIGINAL version of this check was stricter than the sentence above now states, and had to be relaxed.** The first cut of this rule required `ownPhase !== partnerPhase` (did `buildPhases` literally merge the pair into one Phase object) — which, because a Phase is always one contiguous SAME-BANNER run, made it impossible to link two character goals with ANY weapon-banner goal prioritized between them. That's wrong: `E6`'s own shape — `[Odette, OdetteWeapon, Raiden, RaidenWeapon]`, where Odette/Raiden are one real phase's two simultaneous character banners and OdetteWeapon/RaidenWeapon are that same phase's one shared weapon banner — is exactly the real-world case this feature exists to model, and a weapon-banner pull doesn't touch character pity/CR/guaranteed5 at all, so it can't break simultaneity. The check now walks priority-list position directly instead of requiring a `buildPhases` merge: valid as long as no OTHER **5★** character goal sits between the pair (a `4star_character` goal in between is fine too — that's exactly what same-phase anchoring already models, e.g. `[Odette, Alyosha(anchored to both), Miko]`). `buildPhases` itself is UNCHANGED — a linked pair separated by a weapon-banner goal still ends up as two separate Phase objects, which is fine and required no engine changes, since character pity already carries over unconditionally between any two same-banner phases regardless of whether they got merged (see `linkedCharacterGoalId`'s own doc comment in `types.ts`). `E6` was updated to actually link Odette↔Raiden now that it's expressible; new `goalValidation.test.ts` cases cover both the relaxation (weapon goal in between: allowed) and what's still rejected (another 5★ character goal in between: rejected).

The fifteenth-bug's `pendingInTransit`/`isLastUsage` same-banner-skip fix (checks `nextPhase.banner === phase.banner`, not weapon-specific) also already covers two consecutive character phases for free, since it was built banner-agnostic the first time.

### 4★ anchoring is phase-derived, not text-position-derived — seventeenth reported bug (2026-08-19)

**Found by the user hitting three separate, related problems live in the UI:** (1) unlinking a linked 5★ pair (or deleting one side) left the other side's `linkedCharacterGoalId`/`linkedWeaponGoalId` dangling, permanently breaking validation with no way to recover except deleting the goal outright — same for a 4★'s `anchoredFiveStarGoalIds` pointing at a deleted 5★; (2) anchoring a 4★ to two *unlinked* (genuinely sequential) 5★s let whichever phase the 4★ was textually glued to hold the *other* phase's own graduation hostage — chasing `[Odette, Alyosha(4★, anchored to Miko only), Miko]` made Miko literally unwinnable until Alyosha finished, even though her own pulls were happening the whole time; (3) the "listed before its anchor" validation rejection blocked exactly the "pull a 4★ before its 5★ banner even starts, and let a mid-window drop satisfy it" pattern the ninth-reported-bug fix had already gone out of its way to support.

**Root cause of (2) and (3), confirmed by direct code tracing:** a 4★'s "which phase blocks/gates on it" was decided purely by `buildPhases`' raw textual/adjacency membership — completely independent of `anchoredFiveStarGoalIds`. `isPhaseFullyDone` (exact engine) and `stepOnePull`'s `targetIdx` (Monte Carlo, "earliest incomplete goal by raw array position") both required every *textually*-adjacent goal done before focus could advance, with zero awareness that an anchor might name a *different*, later phase.

**Fix — blocking phase becomes `MAX(own textual phase, latest anchor's phase)`** (`phases.ts`'s `resolveFourStarBlockingPhase`): the item's own textual phase still has to be in the MAX, not just dropped in favor of the anchor — the ninth-reported-bug shape (`[Odette, WeaponDetour, Alyosha(anchored to Odette only)]`, her own trailing phase strictly *after* her anchor) needs her own textual phase, not just the anchor's, or that trailing phase would have zero blocking members and vacuously graduate at pull 0. `computeBlockingFourStarGoalIdsForPhase(phases, p, fourStarGoals)` applies this per phase to build the actual blocking set — separate from, and generally a subset/superset-crossing modification of, raw `phase.goals` membership (which is left completely unchanged, since `phaseIndexByGoalId` and the natal-phase-openness exception still need it).

**Unanchored now means "deliberately disconnected," not "attach to whatever's nearby" — fix for (issue 1.5.5), reached the same day mid-report:** `hasFourStarAnchorAmbiguity(phases, fiveStarKind)` counts *distinct phases* containing a same-kind 5★ (not raw goal count — a LINKED/simultaneous pair is one phase, so it doesn't trigger disconnection) and is >= 2 exactly when leaving a 4★'s anchors blank is a real, meaningful choice rather than an unambiguous default. `computeClosedFourStarGoalIdsForPhase`'s unanchored branch: closed in *every* phase when ambiguous (0% until the user actually specifies where she's featured), left open everywhere when there's nothing to disambiguate (today's original fallback, unchanged for the single-phase case).

**This obsoleted two `goalValidation.ts` rules outright, not just made them permissive** — a rejection existing specifically to catch a mismatch that's now structurally impossible isn't a "keep but relax" situation: the "listed before its anchor" rejection (issue 3 — blocking phase is now always `>= min(anchor phases)` by construction) and the "needs to specify which banner(s)" required-anchor error (blank is now always valid, meaning "disconnected") were both removed entirely, not softened. `maxAnchors` was reinterpreted from counting raw anchor ids to counting *distinct resolved phases* among them — otherwise selecting one linked pair (2 ids, 1 phase) already exhausted character's budget of 2, making "span a linked pair *and* a separate third phase" impossible even though the user explicitly asked to keep that spanning capability (see below).

**Issue 1/1.5 (dangling references) — fixed independently, simple and mechanical:** `AppStateContext.tsx`'s `REMOVE_GOAL` now clears any `linkedCharacterGoalId`/`linkedWeaponGoalId`/`anchoredFiveStarGoalIds` reference to the deleted goal on every *other* goal, instead of leaving a permanently-broken validation error with no recovery path. `GoalForm.tsx`/`GoalList.tsx`'s anchor UI was reworked around phase-groups (one checkbox per phase, not per goal — see the sixteenth-reported-bug section above) with the "must pick something" requirement removed and hint text explaining the new blank-means-disconnected semantics; `toggleCharacterAnchorGroup` counts *selected groups* against `maxAnchors`, matching the goalValidation.ts reinterpretation.

**The odds chart (`series`) needed a genuinely new mechanism, not just a phase-loop tweak, to stay exact — the "side-track" — after a scoped design decision from the user.** Once a 4★ can be a *non-blocking* member of its own natal phase (blocking phase resolved elsewhere), `exactEngine.ts`'s phase-loop alignment code — which had always assumed a phase's `phaseGoals` and its blocking requirement were identical — needed to separately track "this specific goal is done" as its own arrival-time distribution, independent of the phase's own handoff timing. Asked via `AskUserQuestion` whether to keep this cross-phase-spanning capability (the `D2`-style "anchor to two different phases, opportunistically accrue in both" shape) or hard-cap anchoring at one phase to sidestep the complexity — **user chose to keep spanning.** A first implementation (marginal subtraction, correcting only the non-blocking goal's own series position) measured up to ~15 percentage points of understatement at *later* series positions (any position between the goal's natal and blocking phase) — asked again whether to ship this documented as a known limitation or build full joint exactness — **user explicitly chose "keep going, attempt full joint exactness now"** over the safer/faster option.

`exactEngine.ts`'s `ActiveSideTrack`: when a phase-loop iteration processes a non-blocking 4★, it opens a parallel `gDoneDensity`/`gPendingDensity` pair (initialized from that phase's own `localPrefixDone`/`graduatedPrefixDone`/`blockingPrefixDone`, all pre-existing `phaseDp.ts` outputs) and threads it forward through every subsequent phase until reaching the goal's own resolved blocking phase, at which point it resolves (`gPendingDensity` convolved against that phase's `blockingPrefixDone`, since by construction that phase's blocking requirement already includes the tracked goal) and merges back into every global series position that was computed using the "already done" stream while the track was active (`affectedGlobalIndices`) — not just the tracked goal's own position, since `series[k]` only requires every goal in the prefix done by the *same* budget N, regardless of which one resolves first. A `natalPhase` guard prevents double-applying the creating phase's own timing on the very first iteration. Only one side-track can be active at a time; a second, simultaneously-active non-blocking goal falls back to the older, simpler marginal-subtraction approximation (`pendingSeriesBridge`) — a genuinely rare shape (two non-blocking 4★s from the same or different natal phases, still both pending at once), kept only for that case, with a global forward monotonicity clamp (`series[k] <= series[k-1]`) as a documented safety net.

**A second, distinct bug surfaced only once the side-track math above was verified working** (found by Monte-Carlo-cross-validating a real weapon-cross-phase-linked scenario, not guessed): a goal *native* to a phase whose blocking set includes an "extra" 4★ (one resolved-blocking here but not textually a member — i.e., exactly the shape the fix above creates) had its own series position computed from `localPrefixDone[k]`, which only ever checks raw `phaseGoals[0..k]` — oblivious to the extra requirement. Concretely: `RaidenWeapon`'s own series position, in a phase whose blocking set is `[RaidenWeapon, X]` (X an earlier, side-tracked 4★ whose blocking phase resolved here), was computed as if X didn't need to be done at all — a real, growing discrepancy (up to ~0.11 at pull 300 in the diagnostic scenario) that's structurally *understatement of the requirement*, not a subtle numerical residual. Fixed by clamping: whenever a phase has such an extra (`hasExtraBlockingFourStars`, computed once per phase), every native member's `localPrefixDone[k]` is elementwise-min'd against `blockingPrefixDone` before use — safe unconditionally, since an extra blocking goal's own natal phase is always strictly earlier than the phase it blocks (by the MAX-formula construction), so its global position always precedes every native member's, meaning the clamp is a correctness fix everywhere it can fire and a no-op everywhere it can't. This dropped the same diagnostic scenario's worst discrepancy from ~0.11 to ~0.02 at pull 300.

**A known, pre-existing residual — not introduced by this fix, but newly *reachable* at the series level by it — was found and correctly left as a documented limitation, not "fixed" further.** Once a side-tracked 4★'s carried-over persistent state feeds into a *later* same-banner phase's own `blockingPrefixDone` (the clamp above), that phase's own graduation timing is derived from a `startDist` that's marginalized over the *earlier* phase's own arrival time — the identical class of approximation already documented under "4★ breakdowns sum across every phase" and the twelfth-reported-bug follow-up's `crCounter` correlation, now shown to affect the series/odds-chart output itself (not just the breakdown panel) whenever this specific side-tracked-adjacent-phase shape is in play. Measured well under 0.01 (an order of magnitude below the already-accepted ~0.007 crCounter bound) in `invariants.test.ts`'s regression coverage. An earlier draft of that test's own comment claimed the series output was fully immune to this class of residual (true only for a single-phase prefix) — corrected in place once this shape proved otherwise, rather than left stale.

Regression tests: `invariants.test.ts`'s "leaving Alyosha unanchored... is a deliberate disconnect" and the corrected "anchored-to-both >= anchored-to-Odette-only" chain-completion test (both epsilons documented inline); `goalTracking.test.ts`'s split unanchored-4★ tests (ambiguous → 0, unambiguous → unchanged fallback — the original single combined test used a LINKED, single-phase `odette`/`miko` fixture pair for what it claimed was the 2-distinct-phase case, silently testing the wrong shape; fixed with genuinely unlinked goals plus a `phases).toHaveLength(2)` guard so the shape can't silently drift back); `goalValidation.test.ts`'s five tests covering the two removed rules, rewritten to assert the now-valid configurations instead of expecting rejections; `exactEngine.test.ts`'s existing "fifteenth reported bug" weapon-cross-phase-linking test (previously failing at diff=0.073 against a 0.03 threshold, now passing).

### `isNextFiveStarClaimBlocked` ignoring a 4★ with zero anchors in the current phase — eighteenth reported bug (2026-08-20)

**Found by a broad, non-pinned exact-vs-Monte-Carlo audit sweep** (`oddsAudit.test.ts`, new this session) run specifically to answer "after all this iterative bug-fixing, do the two engines still agree broadly, not just on the specific shapes already pinned by name." It found a real, severe bug on its very first run: `[Odette, Alyosha(4★, anchored to Miko ONLY, unlinked/sequential), Miko]` — the seventeenth-bug fix's own headline scenario — showed `series[0]` (Odette's own completion, alone) **stuck at exactly 0 for the entire pull budget** in the exact engine, while Monte Carlo correctly showed her won with near-certainty by pull 175. Not a residual — a total, permanent block.

**Root cause:** `goalTracking.ts`'s `isNextFiveStarClaimBlocked` (the same-phase-anchor FIFO-claim gate — see "4★ goals: target level vs. anchoring" above) predates the seventeenth-bug fix and implicitly assumed every 4★ it considers has **at least one** anchor actually present in the phase being checked. Its `allOtherAnchorsAlreadySettled` check treats an anchor **not found** in the current phase's `fiveStarCharGoalIds` as "not in this phase (resolved earlier)" — correct when a multi-anchor 4★ has at least one anchor in-phase (the anchor's cross-phase counterpart genuinely is from an earlier phase, by the existing "sandwiched foreign 5★" validation rule) — but vacuously, *incorrectly* true when **none** of the 4★'s anchors are in this phase at all, which is exactly the new shape the seventeenth-bug fix made possible: a 4★ textually adjacent to one 5★ while blocking-anchored entirely to a **different, later** phase's 5★. Alyosha (textually in Odette's phase, anchored only to Miko's later phase) was treated as "gating Odette's claim on her own incomplete copy count" even though she has zero stake in Odette's phase's own 5★ roster — permanently blocking Odette's FIFO advancement, since Alyosha's own C4 target could take far longer than any pull budget to reach naturally (and even if reached, the bug would just recur for whichever goal comes next).

**Fixed** by adding the same early-out `isFourStarWindowOpenInPhase` (its sibling function, one function above) already had: skip a 4★ from consideration entirely if none of its anchors resolve to a rank in the current phase's `fiveStarCharGoalIds` (`anchorRanksInPhase.length === 0`). Confirmed this fully closes the gap, not just the reported instance: `goalValidation.ts`'s "same-phase anchors must cover EVERY 5★ sharing that phase" rule already forbids a 4★ from anchoring to *some but not all* of a same-phase pair, which is the only other way a partial-overlap version of this bug could otherwise arise (an anchor set spanning one in-phase anchor plus one later-phase anchor) — so "zero anchors in phase" is the only reachable failure shape, and the added early-out covers it completely.

**Confirmed exact-engine-only, not a shared conceptual bug**: Monte Carlo's mirror (`simulate.ts`'s `isFiveStarClaimBlocked`) checks a genuinely different, phase-independent condition — "has the anchor's goal actually been won yet" via the global bitmask — which happens to give the right answer regardless of which phase the anchor nominally belongs to, so it was never affected. This is why cross-validation caught the bug at all (the two engines disagreed) rather than both agreeing on the same wrong answer.

Regression test: `exactEngine.test.ts`'s "eighteenth reported bug" describe block (pins `series[0] > 0.99` by pull 200 — the decisive guard, since pre-fix it was pinned at exactly 0, not a tolerance issue). `oddsAudit.test.ts` — the sweep that found it — is now a **permanent** addition to the suite (not a one-off), since a broad, non-pinned cross-validation pass proved able to catch what seven scenario-specific fixed tests plus dozens of hand-picked regression cases had all missed.

**Also confirmed via this same audit sweep: the already-documented crCounter/persistent-vector time-marginalization residual (twelfth-reported-bug follow-up) reaches a larger peak than previously measured** — up to ~4 percentage points for a single deep-target (C4+, 5+ copies) non-blocking 4★ (previously "~0.7pp" was the largest documented figure, for a different, shallower scenario), and up to ~8 percentage points when **two** such deep-target anchored 4★s compound in the same goal list. Directly confirmed this is still the same bounded, transient class (not a new or growing bug) by checking the full pull-range shape: the discrepancy rises, peaks mid-range, crosses back through zero, and decays to near-0 by a sufficiently large budget (`oddsAudit.test.ts`'s S2 case: peaks at ~7.8pp around pull 305, decays to ~0.04pp by pull 900). Left as-is per the user's own prior, repeated explicit decision not to pursue the architectural fix for this class of approximation — this is new *measurement*, not a new *decision*.

**Follow-up, same day (2026-08-20 later): an unanchored 4★ with EXACTLY ONE same-kind 5★ in the whole list still couldn't be expressed as "on a different, not-yet-added phase" — reported by the user hitting it live in the app, not by casework.** `hasFourStarAnchorAmbiguity` (used by `resolveFourStarBlockingPhase`/`computeClosedFourStarGoalIdsForPhase`'s unanchored branches) only ever treats 2+ candidate phases as real ambiguity — with exactly one candidate, `anchoredFiveStarGoalIds === undefined` (never touched) falls back to "attach to it" (today's deliberate convenience default, so `[Odette, Alyosha]` just works with zero clicks — this is intentional, see `hasFourStarAnchorAmbiguity`'s own doc comment, and a prior session already tried and reverted making even this case "disconnected," since it broke the single most common shape). The problem: with only one candidate ever in play, there was **no way at all** to say "this 4★ is on some OTHER phase I haven't added yet" short of adding a real, phantom placeholder 5★ goal purely to create the 2+-candidate ambiguity the fallback requires to even consider disconnection.

**Went through `AskUserQuestion`, since this is a genuine UX tradeoff with no risk-free answer** — either (a) flip the default so unanchored ALWAYS means disconnected, even with one candidate (matches the user's stated mental model exactly, but costs the common case its zero-click convenience), or (b) keep the single-candidate box pre-checked by default but make it genuinely uncheckable. **User chose (b).**

**Root architectural fix: `anchoredFiveStarGoalIds === undefined` and an EXPLICIT `anchoredFiveStarGoalIds === []` are now different states, not collapsed into one.** Before this, `GoalForm.tsx`'s submit handler explicitly collapsed an empty selection back to `undefined` (`anchors.length > 0 ? anchors : undefined`), and the engine's `!anchors || anchors.length === 0` checks treated both identically — so there was no way to represent "the user affirmatively chose nothing" at all, only "never asked." Now: `undefined` keeps the existing ambiguity-dependent fallback (attach when 0-1 candidates, disconnect when 2+) completely unchanged; an explicit `[]` means **always** disconnected, regardless of candidate count — checked in `phases.ts`'s `resolveFourStarBlockingPhase` and `computeClosedFourStarGoalIdsForPhase` before the ambiguity fallback even runs.

**UI (`GoalForm.tsx`, `GoalList.tsx`): the single-candidate default is now visible AND real, not just a silent engine fallback.** Both files compute an `effectiveAnchors`/`effectiveAnchorsFor` value — the goal's own explicit anchors if it has any (including an explicit empty array), otherwise the single candidate's ids when exactly one phase-group exists, otherwise `[]` — used for both checkbox `checked` state and as the toggle handlers' starting point. `GoalForm.tsx` (the "add new goal" form, which has no saved goal to read from yet) tracks this via local `anchorsTouched` state, reset whenever the goal kind changes or a goal is submitted; the moment the user toggles anything, `anchors`/`anchorsTouched` take over completely and the derived default no longer applies. This is what makes unchecking the one pre-checked box actually submit an explicit `[]` (not a no-op) — previously the checkbox showed unchecked-by-default even when the goal was engine-side attached via fallback, a UI/engine display mismatch this also incidentally fixes.

Regression tests: `goalTracking.test.ts`'s "with exactly ONE same-kind 5-star" test (both halves — `undefined` still auto-attaches, explicit `[]` disconnects — checked side by side against the identical goal-list shape); `exactEngine.test.ts`'s "eighteenth reported bug follow-up" describe block (end-to-end `runExactSimulation`, cross-validated against Monte Carlo for the unchanged-fallback half).

### Graduated 4★ mass froze permanently — trailing continuation phases, plus their own performance cost — nineteenth reported bug (2026-08-20)

**Found by the user hitting two related symptoms live in the app, both traced to one root cause.** `runPhaseDp`'s "graduated" probability mass (mass that has satisfied a phase's `blockingGoals` condition) freezes permanently the instant a banner's *last* real phase finishes — no further 4★ copy accrual ever happens for that banner again, even with substantial pull budget left. Two distinct symptoms:
- **Bug A**: a 4★ goal explicitly disconnected from every listed 5★ phase (`anchoredFiveStarGoalIds: []`, or `undefined` with 2+ candidate phases — see the eighteenth-bug follow-up above) was *supposed* to mean "no chance during any of these specific phases," but the engine's actual behavior was "no chance, ever" — even once every real, listed phase was exhausted and pull budget remained with nothing else to spend it on. `[Odette, Alyosha(disconnected)]` left Alyosha permanently at 0%, not just 0% during Odette's own phase.
- **Bug B**: an already-attached 4★'s constellation/refinement breakdown chart froze the instant her *own* target level was reached, contradicting this file's own documented "the full C0-C6 breakdown is always shown regardless of target level" — e.g. `[Odette, Alyosha(anchored to Odette, target C0)]` showed C6 pinned at whatever value it happened to reach around pull ~160, completely unchanged through pull 500.

**Confirmed via two rounds of `AskUserQuestion`**: disconnected goals should get a real, finite chance once every listed goal resolves and budget remains — an explicit, deliberate reversal of the eighteenth-bug-follow-up session's own "0% forever" decision, made because the user pointed out this exact live-app shape represents a real, wanted use case ("pull for A, then wait for B's own banner and pull for B") that the old semantics made structurally inexpressible. The harder, fuller scope was chosen for the fix (the goal's own *completion*, not just its breakdown chart, becomes achievable) over a narrower breakdown-only fix.

**Mechanism: two synthesized "trailing continuation" phases, appended only for the banner owning the literal last phase of the whole simulation.** The engine models banner focus as strictly sequential/exclusive, so a continuation anywhere else would double-spend the same pull-budget axis across two mutually exclusive stories — a disconnected goal on a *non-tail* banner has no coherent continuation and stays 0% forever, a real, permanent, documented boundary of this fix, not an oversight.
- **Phase R** ("resolution"): created only if the tail banner has disconnected 4★ goal(s) still pending. `.goals = []` (never a real phase member, avoiding double-membership risk); `blockingGoals` = the disconnected goal(s) themselves, referenced by id only — `runPhaseDp` already supports a `blockingGoals` entry that isn't a `phaseGoals` member, since `isGoalDone` for a 4★ only ever reads the banner-wide persistent vector. Graduates once every disconnected goal reaches its own target, giving the *existing* `ActiveSideTrack` mechanism (built for "a 4★'s blocking phase differs from its natal phase") a real phase index to resolve into.
- **Phase C** ("breakdown continuation"): appended right after Phase R (or right after the last real phase, if no Phase R was needed). `blockingGoals = [sentinelGoal]`, a synthetic 4★-kind goal whose `targetId` never matches any real goal's — `isGoalDone` is unconditionally false forever, so this phase *never* graduates and runs for the entire remaining budget, keeping every persistent 4★ of the banner (both newly-resolved disconnected ones and already-graduated attached ones) accruing bonus copies.
- Both phases share one pool-construction rule — everyone open, built directly via `padIds` rather than `computeClosedFourStarGoalIdsForPhase`/`computeCharacterBannerConfigForPhase`/`computeWeaponBannerConfigForPhase` — safe because `MAX_TOTAL_FOUR_STAR_GOALS_PER_BANNER` already caps totals at real roster size. Weapon Fate Points are deliberately *not* reset entering either phase (`isWeaponFatePointsResetOnEntry` is skipped here entirely) — this is a continuation of the same real-time window, not a new Epitomized Path selection.
- `phases.ts`'s `resolveFourStarBlockingPhase`/`computeFourStarBlockingPhaseByGoalId` gained an optional `disconnectedFallbackPhaseIndex(ByBanner)` parameter — computed via a deliberate **two-pass** call: pass 1 (today's real, un-extended `phases` array) discovers which goals resolve to `undefined` under the ordinary rule; pass 2 re-resolves with the tail banner's disconnected goals redirected at Phase R's index. Both passes always use the real, un-extended `phases` array — `hasFourStarAnchorAmbiguity`'s weapon-banner-membership counting would be silently corrupted by an array with Phase R/C already appended, so that array is never passed to either ambiguity-counting function.
- Went through two full rounds of dedicated Plan-agent design validation (not just self-review), both catching real, non-obvious bugs before any code was written: a vacuous-truth instant-graduation bug from an earlier draft's wrong sentinel goal kind (`5star_character` graduates on ANY featured win regardless of the sentinel's fake id — only a 4★-kind sentinel is genuinely unreachable), a silent double-count risk at the Phase-R-to-Phase-C boundary (resolved by the *existing* `nextPhase.banner === phase.banner` skip already in the main loop, from the fifteenth-bug fix), the array-corruption risk described above, and the Fate-Points-reset bug described above.
- `simulate.ts` deliberately does **not** mirror this fix — Monte Carlo already returns `breakdowns: []` unconditionally (Bug B doesn't touch it), and mirroring Phase R/C into `TrialInfo`/`stepOnePull` for Bug A's series fix is a full parallel implementation effort, out of scope for this pass. A doc comment near `stepOnePull`'s phase-scan flags the gap explicitly: for a disconnected-goal-on-the-tail-banner scenario, the exact engine's series output is now *ahead of* (not cross-checked by) Monte Carlo — the reverse of most other documented residuals in this codebase, where Monte Carlo was the trustworthy side. `oddsAudit.test.ts`'s S4 scenario was reshaped (a trailing weapon goal keeps the character banner from being the tail banner) specifically to avoid this now-intentional divergence, rather than cross-validating a path known to disagree by design.

**A real, severe performance regression was discovered immediately after implementing the correctness fix — found by direct measurement, not guessed, matching this app's own established profiling discipline.** Phase C's blocking condition is *unconditionally unsatisfiable* by design, so unlike every other phase (whose active-slice set shrinks over time as mass graduates out into `exitSubstateDist`), Phase C's active-slice set never shrinks — it processes close to the maximum possible `bannerModulus × persistentModulus` state count on *every* pull, for the *entire* remaining pull budget. Measured directly: this app's own documented worst-case scenario (2 four-stars sharing one phase, at the DEFAULT 90-pull budget) went from the earlier session's optimized ~1.7s to **~6.6s** (a ~4x regression) just from Phase C existing at all; a large-budget scenario (2 character 4★s each resuming their own later phase, pullBudget 1000 — a *pre-existing*, previously-fast test, not new this session) failed to complete within a 90-second timeout; a weapon-banner stress scenario at the max total cap (4 goals, pullBudget 700) took ~57s in isolation and worse under full-suite load.

Investigated whether the "skip local pull indices that provably can't be reached" trick that fixed the *original* documented performance regression (see "`runPhaseDp`'s state is organized into slices" above) could apply here too — **it can't, exactly**: that trick relies on `arrivalDensity`'s leading indices being provably, exactly zero, but Phase R/C can legitimately be entered at local pull 0 (e.g. carried-over state that already satisfies everything), so `arrivalDensity[0]` is generically nonzero for real scenarios and the convolution genuinely needs Phase R/C's full local range to stay exact. A genuine EXACT decomposition (evolving the banner-substate and persistent-vector dimensions as independent processes, since transitions mostly don't interact) was also investigated and rejected — `pity4`'s reset behavior couples the two dimensions (a 4★ hit resets both `pity4` *and* the persistent vector on the same pull, and a 5★ hit *also* resets `pity4`, coupling it to the banner's other 5★-related substate too), so a clean marginal split would be an unquantified approximation, not an exact factorization — not something to ship silently.

**Went through `AskUserQuestion` given the real, no-quick-fix tradeoff, offering capping the horizon vs. an approximate decomposition vs. shipping uncapped-but-documented vs. narrowing when Phase C fires at all — user chose capping Phase R/C's own local horizon.** `exactEngine.ts`'s `MAX_CONTINUATION_HORIZON_PULLS` (400) bounds Phase R/C's own local DP range regardless of the global pull budget — `Math.min(maxPulls, MAX_CONTINUATION_HORIZON_PULLS)` — with results padded back to the full global length via `padWithLastValue` (repeats the last computed value, an explicit, deliberate plateau) before being convolved against `arrivalDensity`. This is a genuine, user-approved approximation: past 400 local pulls from whenever Phase R/C is actually entered, a goal's series/breakdown probabilities stop accruing further — the same "plateaus below where it should keep climbing" symptom as the bug this whole mechanism exists to fix, just pushed out past 400 pulls-past-entry instead of past a goal's own target. 400 was chosen as comfortably beyond where even a deep C6/R5 target chasing hard pity repeatedly saturates near-certainty (confirmed directly: the "isolated 4★ chasing C6" regression test's own large-budget check, C6 > 0.9 by pull 900, already converges well inside the 400-pull cap — its pass under the cap confirms this, not just an assumption).

**Measured result after the cap**: the previously-timing-out 1000-pull-budget test and the full `exactEngine.test.ts` suite (including its own new large-budget "keeps accruing past target" test) both pass again, comfortably under their timeouts. The weapon-banner max-cap stress scenario (`oddsAudit.test.ts`'s S7 — persistentModulus 1296, the single largest reachable state count on either banner) still takes ~144s even with the cap — genuinely the most expensive scenario in the suite, given its state space dwarfs anything else — so its own test timeout was widened (120s → 240s) rather than shrinking the global cap further and eroding the accrual window for realistic, non-stress-test goal lists. The DEFAULT-budget documented worst case (90 pulls) is **not** helped by the cap at all (90 < 400, so Phase C's own local horizon is already bounded by the global budget regardless) and remains at the full ~4x regression (~1.7s → ~5.9s) measured before the cap — a real, smaller, accepted residual cost of Phase C existing at all for any goal list with persistent 4★ goals on its tail banner, distinct from the large-budget blowup the cap specifically targets.

Regression tests: `exactEngine.test.ts`'s rewritten "explicit empty anchors" and "isolated 4★ goal... keeps accruing bonus copies past its own target" tests, plus a new "trailing continuation phases" describe block (two disconnected goals sharing the tail banner both eventually resolve; a disconnected goal on the *non*-tail banner stays 0% forever, locking in the documented scope boundary). `invariants.test.ts`'s rewritten "leaving Alyosha unanchored..." test (now asserting a real, measured ~15.7%-at-150-pulls value with margin, not a near-zero bound, plus a new large-budget check that she and the full chain both approach certainty) and its pre-existing "two 4★s, both anchored to Odette, each resuming in its own separate later phase" test (unchanged assertions, now passing again post-cap). `oddsAudit.test.ts`'s S4 (reshaped to avoid the intentional exact-vs-Monte-Carlo divergence) and S7 (widened timeout).

### A side-tracked 4★'s own series position wrongly required its blocking phase's OTHER members too — twentieth reported bug (2026-08-20)

**Found by the user live in the app, immediately after the nineteenth-bug fix shipped.** `[Odette, Alyosha(4★, C0 target, anchored to Miko only), Miko]` — the exact "D2"/seventeenth-bug shape the side-track mechanism exists to handle — showed the odds chart's "Odette + Alyosha" curve *completely overlapping* "Odette + Alyosha + Miko," at every pull count, with no visible gap between them. The user's own reasoning was exactly right: "at any pull count you are much more likely to have gotten odette + alyosha than odette + alyosha + miko" — Alyosha (a shallow C0 target) very often finishes long before Miko's own multi-dozen-pull 5★ draw even resolves, so these two series entries should diverge sharply, not coincide.

**Root cause, confirmed by direct code trace and reproduction, not guessed:** `exactEngine.ts`'s `ActiveSideTrack` resolution (built for the seventeenth bug, to let a 4★ anchored to a *later* phase's 5★ still complete) resolves the tracked goal's own series position by convolving its pending mass against `result.blockingPrefixDone` — but that's the *entire* blocking phase's own graduation condition, not a metric scoped to the tracked goal alone. Whenever the blocking phase has ANY other blocking member of its own — here, Miko's own native 5★ pull — `blockingPrefixDone` there means "Miko **and** Alyosha both done," so resolving "is Alyosha done" was silently, incorrectly ALSO requiring Miko. This affected both call sites that resolve a side track: the main phase loop's own resolution branch, and the nineteenth-bug's Phase R resolution branch (which has the identical failure mode whenever Phase R has 2+ disconnected goals sharing the tail banner, requiring all of them jointly instead of just the one goal being resolved).

**Fixed** by `goalAloneDoneCumulative(result, fi, level)` — sums `activeLevelCounts[fi][level] + graduatedLevelCounts[fi][level]` (the SAME per-goal, phase-graduation-independent metric the constellation/refinement breakdown panel already relies on) instead of reusing `blockingPrefixDone`. `ActiveSideTrack` gained `fi`/`level` fields (populated at track-creation time, same values already available there) so the resolution sites can look up the tracked goal's own metric instead of the phase-wide one.

**Directly answers "shouldn't testing have caught this":** yes — and it nearly did. `oddsAudit.test.ts`'s S3 scenario exercises the *exact same* code path (a 4★ anchored only to a later phase whose blocking phase has its own native 5★), but with a *deep* C4 target — at that depth, the tracked goal's own natural resolution time is comparable to or longer than the blocking phase's own 5★ draw, so the bug's effect (an extra, unnecessary requirement) stayed small enough to hide under S3's 5% cross-validation tolerance. A *shallow* target (C0) is what makes the gap large and obvious, since the tracked goal then very often finishes long before the blocking phase's own 5★ even resolves. This is a real, concrete lesson for this test suite: varying target *depth*, not just goal-list *shape*, matters for a scenario's power to catch this class of bug — noted directly on the new regression test's own doc comment so it isn't lost.

**Verified:** reproduced the user's exact scenario directly and confirmed the fix — before, series[1] (Odette+Alyosha) was byte-identical to series[2] (Odette+Alyosha+Miko) at every pull count; after, they diverge correctly (e.g. at pull 90: 29.1% vs 4.4%; at pull 300: 99.8% vs 94.9%), and both values were independently cross-validated against Monte Carlo (worst discrepancy ~0.2 percentage points across the whole pull range — well within normal sampling noise for a 500k-trial run, confirming the fixed exact values are correct, not merely different from the buggy ones). Full test suite green after the fix (one test, S6, timed out only under full-suite parallel resource contention — confirmed to pass cleanly in ~80s when run in isolation, and confirmed its own goal list never touches this fix's code path at all, so this was not a regression). Regression test: `exactEngine.test.ts`'s "twentieth reported bug" describe block (the C0-target reproduction, decisive `series[1] > series[2] + 0.01` assertion at every sampled pull, monotonicity checks, and Monte Carlo cross-validation).

### A disconnected 4★ gets its own real phase, at its own priority position — twentieth reported bug follow-up (2026-08-21)

**Superseded the nineteenth bug's "Phase R" mechanism entirely.** That fix gave a disconnected 4★ (no anchor, or ambiguous) a real chance to complete by appending a synthetic "Phase R" — but *only* after the tail banner's very last real phase, regardless of where the disconnected goal actually sits in priority order. ### 4★ breakdowns sum across every phase of a banner, not just the goal's own phase

`exactEngine.ts` used to emit each 4★ goal's constellation/refinement breakdown from only the *last* phase that ever used its banner, since that phase's persistent-vector math already reflects everything carried forward from earlier phases. That's true for probability mass that has *already reached* that last phase — but it silently dropped mass still active in an *earlier* phase of the same banner (e.g. still working toward the first 5★, before a weapon-banner detour even happens), making the breakdown read as if "every earlier goal in the list is also done" were a hidden prerequisite — and, worse, produced a visible non-monotonic *cliff*: as mass graduated the earlier phase (say, got the 5★) but hadn't yet finished an intervening weapon-banner goal, it fell into a gap neither the earlier phase (no longer "active" there) nor the later phase (hasn't arrived yet) credited, before "recovering" once enough mass finished the detour. A cumulative "reached by pull N" curve must never decrease in N — a copy once obtained is never lost — so this was a real, user-visible bug, not just a stylistic one.

`phaseDp.ts` reports `activeLevelCounts` (mass still active within that phase) and `graduatedLevelCounts` (mass that has satisfied the phase's own goals, frozen at graduation) as *separate* arrays. `exactEngine.ts` sums three contributions per banner: (1) every phase's `activeLevelCounts`, each convolved with that phase's own arrival density (mass hasn't left this banner yet); (2) for a banner's *last*-used phase, its `graduatedLevelCounts` directly (nothing left to evolve through); (3) for every *non-last* phase, its graduated mass is instead "in transit" toward the next phase of the same banner — credited via `convolve(globalGraduationDensity, survivalOfInterveningPhase)`, where `survivalOfInterveningPhase = 1 − thatPhase'sOwnCompletionCDF` — exploiting that the intervening phase's own duration is independent of both when the graduation happened and what level was reached (it doesn't touch this banner's state at all). Skipping term (3) is what caused the cliff; adding it (`pendingInTransit`, resolved by the very next phase processed) closes the gap.

A second, related bug: a state that *already* satisfies a phase's goal the instant it's entered (carried over from an earlier phase) used to sit in `active` through one extra, un-graduated pull before being recognized as done — since `isPhaseFullyDone` was only ever checked on a post-transition vector, never on the raw entering state. That extra pull gave it one more undue chance to accrue an additional copy. Fixed by checking `isPhaseFullyDone` on the entering distribution itself, before any transitions, splitting already-done mass straight into `exitSubstateDist`/`graduatedLevelCounts` at local pull 0.

**Known remaining limitation**: pity/CR/fate reset (or land in a small bounded range) near a win *when nothing extends the phase past that win* — the arrival-density convolution trick above is exact only in that case. A 4★'s copy count never resets — it only grows — so it's genuinely correlated with how long the *preceding* phase took (a longer detour means more opportunistic 4★ pulls happened along the way), a correlation the time-marginalized handoff doesn't fully preserve. This can produce a tiny (confirmed well under 0.1 percentage point at this app's realistic pull-budget range, growing slowly at much larger budgets like 300+) non-monotonic wobble in a 4★ breakdown that follows a different-banner detour. A fully exact fix would re-run the downstream phase separately per starting copy count instead of from one merged distribution — a real architectural change, not implemented, since the residual is far below what's visible in a UI that rounds to one decimal place.

**Correction, 2026-08-19: "pity/CR/fate reset near a win, so the trick is exact for them" is WRONG whenever something extends the phase past that win** — see the twelfth-reported-bug follow-up above ("A separate, smaller residual discrepancy...", now root-caused) for the full story. `crCounter` specifically does NOT simply reset the way `pity5` does — a same-phase 4★ that keeps a phase running well past its own 5★'s win gives `crCounter` room to drift (more extra pulls = more chances for a 50/50 loss), and that drift is genuinely correlated with how long the extra chase took. The SAME marginalization gap this section describes for 4★ copy counts applies to `crCounter` too, in that specific shape — and unlike the 4★-copy-count residual (confirmed tiny, well under 0.1pp), the `crCounter` version was measured at up to ~0.7 percentage points, a real, visible error in the exact engine's own odds chart, not just a breakdown-panel nicety. Left as a known, documented limitation rather than fixed (same architectural fix would be needed as described above), per explicit user decision.

**Update, 2026-08-19 (fifteenth reported bug's own testing):** the same residual can be noticeably LARGER — up to ~0.7 percentage points, at levels *above* a 4★'s own `targetLevel` (i.e. still-growing copy counts past the point priority/focus already moved on), for a phase-boundary crossing where the very NEXT phase is the *same* banner reoccurring immediately (no real different-banner detour in between at all — see "5★-weapon window linking is explicit, not inferred from adjacency" below for how this shape becomes reachable). Directly A/B-tested against the pre-fix code path for this same shape: the OLD (always-defer-and-bridge-via-survival) behavior was far worse — a genuine double-count producing breakdown values *exceeding probability 1* (up to 1.43) and errors up to 61 percentage points at the 4★'s own target level, not just an amplified version of this already-known correlation residual. The fix (skip both the direct-add and the deferred-bridge paths entirely when the next phase is the same banner — see `exactEngine.ts`'s comment on this branch) reduces the target-level error to an exact match; the larger-than-previously-measured residual at levels *above* target is this same pre-existing, architectural limitation, confirmed via a direct comparison to not be something the fix itself introduces. Still not implemented (same reasoning as above), but worth knowing the "well under 0.1pp" figure was specific to the different-banner-detour shape it was originally measured against, not a universal bound.

### Banner config is derived from goals, per phase, not configured separately

Each banner's `featured4StarIds`/`featured4WeaponIds`/`chosenWeaponId`/`otherFeaturedWeaponId` is derived from whatever goals reference them — but, since the fixes described in "5★-weapon identity is scoped to its own phase" above, this happens **fresh per phase**, inside the engine, not once globally. `phases.ts`'s `computeCharacterBannerConfigForPhase`/`computeWeaponBannerConfigForPhase` build each phase's own config from that phase's own active/natal goals (padding with anonymous placeholder ids up to the real pool size — 3 character 4★s, 5 weapon 4★s — so the simulated odds for named goals stay correct even when some rate-up slots are unnamed), called once per phase in `exactEngine.ts`'s phase loop and precomputed once per phase in `simulate.ts`'s `TrialInfo` (`characterConfigByPhase`/`weaponConfigByPhase`). `SimulationInput` itself no longer carries a static config at all — `characterBanner` only has `{ state, featured5StarId }` (the one field that's genuinely global, since 5★-character matching is identity-agnostic) and `weaponBanner` only has `{ state }`. `state/buildSimulationInput.ts` correspondingly just forwards `state.goals` through — it no longer builds any pool/identity itself. There is no separate "configure the banner's featured pool" UI step; naming a goal is enough. A goal's `targetId` is set equal to its own `id` at creation time (`AppStateContext.tsx`'s `ADD_GOAL`) — the two are always in sync in this app, but engine code should key off `targetId`, not `id`, since that's the identity space pull outcomes actually live in (a prior bug mixed these up in `goalTracking.ts`; see its comment on `fourStarIndex`).

### Capturing Radiance has two selectable models, on purpose

HoYoverse has never published the real formula — this is genuine, ongoing community speculation, not just an engineering shortcut. `capturingRadiance.ts` implements two community hypotheses behind `CRModel`/`CR_MODELS`, selected at the `SimulationInput.crModelId` level:

- **`'A'`** (default): counter `r` starts at 0 and only increments on a *loss* (capped at 3); a win at `r=0` or `r=1` decrements to 0; at `r=2`, `params.r2TotalWinRate` (default 0.55, user-adjustable 0.5–1.0) is the *total* win chance there — organic 50% plus some sliver of Capturing-Radiance-boosted chance on top — and *either* kind of win at `r=2` decrements to **1, not 0**; at `r=3` the win is guaranteed (mechanically ~50% organic + guaranteed-CR-if-lost, but externally always a win) and also decrements to **1, not 0**. Cross-checked against OneBST's cited 4M-pull community analysis and against an independent implementation (HuTaoSite's gachacalc.tsx, which documents this exact same r=2/r=3 decrement-to-1 behavior) — and confirmed, during the ground-truth audit, to match the user's own long-standing understanding of the mechanic exactly, transition for transition. Treat this as the user's endorsed default; there's no known reason to change it.
- **`'B'`**: a flatter, simpler curve with no organic/CR split — win rate is just `{r=0: 50%, r=1: 52.5%, r=2: 75%, r=3: 100%}`, and **any** win (including the guaranteed r=3 one) resets `r` fully to 0. The two real differences from A: it starts nudging the odds up one loss earlier (52.5% at r=1, where A is still a plain 50/50), and it never has A's "still primed at 1, not fully reset" behavior after a Capturing Radiance trigger. Kept as the `genshin-wishes.com`-style alternative some other public calculators use.

Don't collapse these into one "true" formula; the uncertainty is real and both models are tested independently (`capturingRadiance.test.ts`) and cross-checked end-to-end (`exactEngine.test.ts`).

### State encoding

`pity4` (4★ pity) is capped at 9 in the transition functions (`characterBanner.ts`/`weaponBanner.ts`) — lossless, since the 4★ rate is flat at 100% beyond that, but it's what keeps `stateCodec.ts`'s fixed-size integer encoding valid (without the cap, `pity4` can in principle exceed 9 when repeated 5★ pulls take precedence over 4★ pulls in the resolution order). `pity5` needs no such cap; it's naturally bounded by hard pity.
