# Architecture

How this engine actually works, as of 2026-08-30. Current-state only — no bug-by-bug narrative; see [CHANGELOG.md](CHANGELOG.md) for the full dated history behind any decision mentioned here, and [FOCUS_RULES.md](FOCUS_RULES.md) for a worked-example lookup table of exactly what the engine assumes a player does, pull by pull.

## Module layout

Everything under `src/engine/` is pure TypeScript with no React/DOM dependency, and is unit-tested directly (`src/engine/__tests__/`). `src/state/` and `src/components/` are the UI layer that consumes it.

- `pity.ts`, `capturingRadiance.ts`, `characterBanner.ts`, `weaponBanner.ts`, `stateCodec.ts` — single-pull mechanics for one banner: exhaustive, deterministic `(probability, outcome, nextState)` transition lists, ground-truthed against real Genshin mechanics.
- `goalKinds.ts` — per-kind rules shared by the engine, validator and UI: banner of a kind, copies needed for a 4★ target level, default levels, level labels, anchor limits.
- `goalTracking.ts` — the phase-local vs. persistent goal-tracking state machine (`PhaseLocalSpec`/`PersistentSpec`), shared by both engines below.
- `phases.ts` — groups a priority-ordered goal list into "phases" and derives every phase-scoped config/closure rule from them. Pure function of `goals` alone — never touches pull budget.
- `phaseDp.ts` — the exact DP for one phase.
- `exactEngine.ts` (`runExactSimulation`) — **the live runtime engine.** Stitches phases together into the app's actual odds chart and constellation/refinement breakdowns. Exact probability propagation, no sampling.
- `simulate.ts` (`runSimulation`) — a Monte Carlo implementation of the *same* mechanics, kept only as an independent cross-validation tool for tests (`exactEngine.test.ts`, `oddsAudit.test.ts`) — never called from the shipped app or the worker. It produces 4★ breakdowns too (tracking copies past each target and through the trailing continuation), so the breakdown panel is cross-checked as well.
- `trace.ts` — narrates one concrete, reproducible pull-by-pull playthrough in plain language (reuses `simulate.ts`'s `stepOnePull`), for "why does the engine believe this," not "is the number right." Has both a test-suite consumer (`trace.survey.test.ts`) and a live UI panel (`TracePanel.tsx`).
- `sliceResult.ts` — truncates an already-computed larger-budget result down to a smaller one, for the pull-budget-decrease cache in `useSimulation.ts`.
- `exactDp.ts` — single-banner exact-DP ground truth, test-only (cross-validates the phase-based engine and Monte Carlo against an independent, simpler computation).
- `goalValidation.ts` — rejects goal-list configurations that don't correspond to any real Genshin patch structure, or that would make the DP too expensive.
- `worker.ts` / `src/state/useSimulation.ts` — the live engine runs in a Web Worker via a debounced hook.

**Golden rule:** when you change goal-matching or tracking semantics, mirror the change in `phaseDp.ts`/`goalTracking.ts` (exact) AND `simulate.ts` (Monte Carlo) — `exactEngine.test.ts` cross-validates the two and will (correctly) start failing if they drift.

## Phase decomposition — the core algorithmic idea

A naive joint DP over both banners' full state spaces simultaneously is intractable (their product is tens of millions of states). The engine instead:

1. **Groups the priority-ordered goal list into phases** (`phases.ts`'s `buildPhases`) — banner focus is defined as "the banner of the highest-priority incomplete goal," which only depends on the fixed priority order, not on completion timing, so focus only ever changes at a phase boundary. `buildPhases` is a pure function of `goals` alone (never of pull budget), built in two passes:
   - **Baseline pass**: a maximal run of consecutive same-banner goals is one phase — UNLESS two adjacent `5star_weapon` goals aren't explicitly linked (`Goal.linkedWeaponGoalId`) or two adjacent `5star_character` goals aren't explicitly linked (`Goal.linkedCharacterGoalId`), in which case a phase boundary is forced even though they're the same banner and adjacent. Linking is explicit, not inferred from adjacency — see "Window linking" below.
   - **Disconnected-goal split pass**: a 4★ goal with no coherent anchor to any listed 5★ window (`computeDisconnectedFourStarGoalIds`) becomes the sole member of its own isolated phase, forced apart from its neighbors, at its own priority-list position — never merged with an adjacent disconnected goal even if there are several in a row.
2. **Runs each phase's own compact DP** (`phaseDp.ts`'s `runPhaseDp`) — banner pity/CR/fate state × a phase-local 5★-character FIFO counter × a banner-wide persistent goal-tracking vector (see "Goal tracking" below). Goals sharing a phase's banner are checked opportunistically on every pull, not sequentially by priority.
3. **Stitches phases together** by convolving each phase's own local-pull-indexed completion-time distribution with the accumulated global arrival-time distribution from every phase before it (`exactEngine.ts`'s `convolve`/`cumulativeToDensity`), so results land correctly on the *global* pull axis even though each phase's own DP only knows its local pull count.
4. **When the same banner reoccurs in a later phase** (e.g. character → weapon → character), that later phase's starting state distribution is the earlier phase's own exit-state distribution, normalized — not the user's raw input state. This carries BOTH the banner's own pity/CR/fate substate and the persistent tracking vector across the reoccurrence — and, for the one case described under "Window linking" below, the phase-local 5★-character FIFO vector too.

### `runPhaseDp`'s internal structure: "slices," not one flat map

Within one phase's own DP, a pull's effect factors into two independent pieces: which banner substate (`bannerCode` — pity/CR/fate) you land in (driven purely by `transitionCharacterBanner`/`transitionWeaponBanner`), and what happens to the goal-tracking vectors (`persistentCode`/`phaseCode`, driven purely by `updateGoalTracking`/`isGoalDone`/`isPhaseFullyDone`) — and the goal-tracking side depends only on *which outcome shape occurred* (rarity + kind + itemId), never on the specific `bannerCode` that produced it. State is grouped into "slices," one dense `Float64Array` (indexed by `bannerCode`) per distinct `(persistentCode, phaseCode)` pair actually reached. Per pull, per slice: the goal-tracking result is computed once per outcome shape (a fixed, small set derived from the banner config — `enumerateOutcomeShapes`), then applied to every banner substate in that slice as pure array arithmetic. This is the single biggest performance lever in the engine — see "Performance" below for the full history of tuning it.

`PhaseDpResult` reports two things about a persistent 4★'s copy count per pull, kept separate rather than summed: `activeLevelCounts` (mass still active in this phase, hasn't satisfied the phase's blocking goals yet) and `graduatedLevelCounts` (mass that has, frozen at graduation). `exactEngine.ts` needs both separately to correctly sum a 4★'s FULL breakdown across every phase of its banner without double-counting or leaving gaps (see "4★ breakdowns span every phase" below).

## Goal tracking (`goalTracking.ts`)

Two tracking vectors, for two genuinely different lifetimes:

- **Phase-local** (`PhaseLocalSpec`, resets every phase): the shared FIFO counter for this phase's own `5star_character` goals. Resets because a `5star_character` goal in a *later* phase genuinely represents a separate, later win, not something claimable once focus has moved on.
- **Persistent** (`PersistentSpec`, carries across *every* phase of a banner, built once from the WHOLE goal list): `5star_weapon` identity flags and `4star_character`/`4star_weapon` copy counts (0-7 / 0-5, i.e. C0-C6 / R1-R5). These persist because multiple 4★s (and both featured weapons) genuinely coexist on a banner and can be opportunistically obtained on ANY pull of that banner, regardless of which phase a goal's own priority slot lands in.

`PersistentSpec.dims` (and its mixed-radix `encodeVector`/`decodeVector`) is derived from the whole goal list's 4★/5★-weapon goals for a banner — **this is a fixed-shape encoding, not appendable**: adding a goal changes `dims` itself, not just what's stored at existing indices. This is why "cheap incremental goal-add" isn't feasible without deep rework (see "Known limitations").

### 4★ goals: target level vs. anchoring — two distinct concepts

- **`targetLevel`** (C0-C6 / R1-R5) controls *when a goal counts as done* for priority/banner-focus purposes. The full breakdown is always computed regardless of this setting.
- **`anchoredFiveStarGoalIds`** controls *how long the 4★ stays trackable at all*, independent of its own target — models the real Genshin structure where one phase (~3 weeks) runs two simultaneous 5★ character banners sharing the same 3 featured 4★ characters, plus one 5★ weapon banner featuring both its 5★ weapons. A different phase has its own, generally different, roster. So `4star_character` gets up to 2 anchors (one per simultaneous character banner), `4star_weapon` gets at most 1 (only one weapon banner runs per phase).
  - A 4★'s BLOCKING phase (which phase's graduation it gates) is `resolveFourStarBlockingPhase`: its own natal phase, UNLESS that natal phase isn't itself one of its named anchors, in which case it's the LATEST anchor's phase instead. Never just "the latest anchor, always" — a 4★ whose own natal phase genuinely is one of her anchors blocks *there*, holding up that phase's own graduation (and, via the FIFO-carry mechanism under "Window linking" below, letting an incidental extra featured win during that hold-up roll over onto a later linked 5★'s still-open slot) rather than always deferring past it. Only when the natal phase ISN'T a real anchor window for her at all does she become a non-blocking "passenger," with her real completion odds computed against her true, later blocking phase instead (`exactEngine.ts`'s "side-track" mechanism, `ActiveSideTrack` — see "Performance"/known-limitations note on its own residual below).
  - `anchoredFiveStarGoalIds === undefined` means "attach to the one unambiguous phase" (0-1 same-kind 5★ exists anywhere) or "deliberately disconnected" (2+ exist, real ambiguity, nothing to default-attach to) — `computeDisconnectedFourStarGoalIds` decides which. An EXPLICIT empty array `[]` always means disconnected, regardless of ambiguity — the two are deliberately different states (`undefined` ≠ `[]`), since without that distinction there was no way to say "disconnect this even though there's only one candidate."
  - A same-phase anchor set must cover EVERY 5★ sharing that phase, not just some — `goalValidation.ts` enforces this, since real simultaneous same-phase banners always share the identical 4★ roster.
  - `isNextFiveStarClaimBlocked` (`goalTracking.ts`) also gates the next 5★-character CLAIM itself, not just 4★ copy accrual, whenever a same-phase 4★ is anchored only to an already-claimed 5★ — without this, "anchored to one banner" and "anchored to both" would compute identical odds whenever the two 5★s share a phase.

### Window linking is explicit, never inferred from adjacency

- **`Goal.linkedWeaponGoalId`** (5★ weapon only): points at the OTHER `5star_weapon` goal sharing the SAME real weapon-banner window (shared Epitomized Path pool, shared Fate Point progress, opportunistic crediting either direction). Symmetric, at most one partner. Absence means "different window," even if adjacent in priority order.
- **`Goal.linkedCharacterGoalId`** (5★ character only): points at the OTHER `5star_character` goal that's genuinely SIMULTANEOUS — two separate banners running at once, sharing pity/guaranteed5/crCounter state and the 4★ roster, but NOT sharing a single 50/50 (each is its own banner). Absence means "different, sequential phase." A linked pair must have no OTHER `5star_character` goal between them in priority order (a 4★ or weapon-banner goal in between is fine — that's exactly what same-phase anchoring / concurrent weapon banners model).
- Both fields exist because adjacency alone is ambiguous in both directions: real phases naturally interleave a shared weapon banner with two simultaneous character banners (`[Odette, OdetteWeapon, Raiden, RaidenWeapon]`, Odette↔Raiden linked), and conversely two adjacent same-kind 5★ goals might genuinely be two unrelated sequential phases with nothing shared at all.

#### A linked character pair split apart by a detour still shares one real FIFO window

`buildPhases` only merges a linked pair into one literal `Phase` object when they're *literally* adjacent — it never searches across a gap (see `buildPhases`'s own doc comment). When something sits between them (an interleaved weapon-banner detour, most commonly), the pair ends up as two separate `Phase` objects, but they still represent the SAME real-time window — `phases.ts`'s `computeCharacterWindowPartnerPhase`/`computeCharacterWindowGoalsForPhase` find and combine such a pair (mirroring `computeWeaponWindowGoalsForPhase`'s own search pattern, solving a different problem — see their doc comments for why weapon linking never needed this: a weapon pull's identity is directly observable, so it's never routed through a FIFO at all).

`exactEngine.ts` builds BOTH phases' `PhaseLocalSpec` from this combined, priority-ordered goal list (`effectivePhaseGoals`) instead of each phase's own native members, so a featured win claimed during the FIRST phase's own extra pulls — held open past its own 5★'s claim by a same-window 4★ still short of target, per the blocking-phase rule above — correctly rolls over onto the SECOND phase's still-open slot instead of vanishing. This requires the phase-local FIFO code (`phaseCode`) to survive the reoccurrence handoff, unlike the ordinary case where it always resets to 0 — `phaseDp.ts`'s `exitSubstateDist`/`startDist` keys are therefore always 3-part (`bannerCode`, `persistentCode`, `phaseCode`), with `exactEngine.ts` deciding, per transition, whether to preserve the decoded `phaseCode` (the second phase of a window pair) or reset it to 0 (every ordinary reoccurrence). Costs nothing for the ordinary case: an ordinary phase's own native 5★s always block it, so `phaseCode` is pinned to one fixed value at the point of graduation regardless, adding no new distinct keys. `simulate.ts` mirrors this with its own `characterWindowPartnerByPhase`, widening `isFiveStarClaimBlocked`'s/`applyOutcome`'s same-phase checks to also accept a phase's window partner — simpler there, since its `bitmask` is already global rather than phase-scoped.

### Why 5★ character goals ignore identity

The character banner config only tracks one currently-featured 5★ id. A second `5star_character` goal doesn't name a different character — it represents "whoever's featured on a future rerun." Matching checks only rarity+featured, not itemId; the earliest pending such goal claims each featured win (FIFO). 4★ and weapon goals, by contrast, are identity-specific, since multiple named options genuinely coexist on one banner at once.

## Banner mechanics

### Character banner (`characterBanner.ts`, `capturingRadiance.ts`)

Standard pity: 0.6% base 5★ rate, soft pity from pull 74, hard pity at 90 (`pity.ts`'s `char5Rate`). A lost 50/50 sets `guaranteed5`, forcing the next 5★ featured. Capturing Radiance (the boosted-odds-after-repeated-losses mechanic) has **two selectable community-hypothesis models**, since HoYoverse has never published the real formula — this is genuine ongoing speculation, not an engineering shortcut:
- **Hypothesis A** (default, `crModelId: 'A'`): counter `r` starts at 0, increments only on a loss (capped at 3); wins at `r=0`/`r=1` decrement to 0; at `r=2`, `r2TotalWinRate` (default 0.55, user-adjustable) is the *total* win chance and any win there decrements to **1, not 0**; at `r=3` the win is guaranteed and also decrements to **1, not 0**. Cross-checked against community data and confirmed to match the user's own long-standing mental model — treat this as the endorsed default.
- **Hypothesis B**: a flatter curve, `{r=0: 50%, r=1: 52.5%, r=2: 75%, r=3: 100%}`, any win resets fully to 0.

Don't collapse these into one "true" formula — the uncertainty is real.

### Weapon banner (`weaponBanner.ts`)

Two genuinely independent mechanics, confirmed against real Genshin mechanics:
- **`guaranteed5`** — the banner's own 75/25 pity, parallel to the character banner's 50/50. After a standard (off-banner) 5★ weapon, the next 5★ is guaranteed to be one of the 2 event weapons (a 50/50 between them on its own). Carries across weapon-banner phases — it's a pity mechanic, not tied to a phase's Epitomized Path selection.
- **`fatePoints` (Epitomized Path)** — earned by getting a 5★ weapon that isn't your chosen one. Once 1, it fully overrides the next 5★ to be 100% chosen, regardless of `guaranteed5`. **Resets to 0 at every NEW weapon-banner phase** (a per-phase selection) — the reset lives at the phase-boundary layer in both engines (`exactEngine.ts`'s `resetWeaponFatePoints`, `simulate.ts`'s `resetFatePointsOnEntry`), gated by `phases.ts`'s `isWeaponFatePointsResetOnEntry`, which is SKIPPED when the reoccurring phase's own weapon goal is linked to the goal whose phase precedes it (a linked pair is one continuous EP window split by a detour, not a new selection).
- **Epitomized Path retarget**: once a phase's first `5star_weapon` goal is claimed, a rational player retargets EP to the second — `phases.ts`'s `computeWeaponBannerConfigAfterFirstClaimedForPhase` supplies a swapped config; `phaseDp.ts` selects between the two adapters PER SLICE based on whether that slice's own persistent vector already shows the first weapon as obtained.

## Banner config is derived from goals, per phase — not configured separately

Each banner's featured-4★ pool / chosen-weapon identity is derived fresh, per phase, from whichever goals are actually active in that specific phase (`phases.ts`'s `computeCharacterBannerConfigForPhase`/`computeWeaponBannerConfigForPhase`/`computeClosedFourStarGoalIdsForPhase`/`computeClosedFiveStarWeaponTargetIdsForPhase`) — padded with anonymous placeholder ids up to the real pool size (3 character 4★s, 5 weapon 4★s) so a named goal's own odds stay correct even when some rate-up slots are unnamed. There is no separate "configure the banner" UI step; naming a goal is enough, and a goal's `targetId` equals its own `id` (`AppStateContext.tsx`'s `ADD_GOAL`).

## Performance architecture

- **`runPhaseDp`'s slice restructuring** (see above) is the foundational optimization — goal-tracking results are computed once per outcome shape per slice per pull, not once per `(bannerCode, slice)` combination, then applied via pure array arithmetic. A follow-up pass replaced string-keyed lookups (`perOutcome`, `getTransitions`'s cache) with integer-indexed arrays and removed an eagerly-maintained `totalMass` map in favor of lazy summation.
- **`MAX_TOTAL_FOUR_STAR_GOALS_PER_BANNER`** (`goalValidation.ts`, 3 character / 4 weapon) bounds `PersistentSpec`'s state-space cost — each additional 4★ goal multiplies the state space 8x (character, C0-C6) or 6x (weapon, R1-R5), and this cost compounds far worse than a naive per-goal reading suggests once a banner is reused across phases (a goal whose value froze after its own phase graduated still rides along as a live, varying dimension in every later phase's state space). Raising this needs a real profiling pass and likely a deeper fix (phase-scoped, not banner-wide, `PersistentSpec` dimensionality) — see "Known limitations."
- **`MAX_ACTIVE_FOUR_STAR_GOALS_PER_PHASE`** (3 character / 5 weapon) is the separate, correctness-motivated cap matching the real per-phase roster size — never move this one for performance reasons.
- **`MAX_DISCONNECTED_FOUR_STAR_GOALS_PER_BANNER`** (2 character / 3 weapon) bounds how many 4★s can be simultaneously disconnected — each disconnected 4★ gets her own real, isolated phase (own `PersistentSpec` state-space cost paid again per phase), so this compounds the same way as the total-goals cap.
- **`MAX_CONTINUATION_HORIZON_PULLS`** (400, `exactEngine.ts`) caps two computations whose cost never tapers off, independent of the configured budget: the trailing continuation (below) and a disconnected 4★'s own isolated phase. An ordinary phase gets cheaper as mass graduates out; these keep their full state space for their whole range. A disconnected phase runs to 400 local pulls and is padded forward with its last value; continuation mass stops pulling after local pull 400 of the last phase. A real, small, user-approved plateau past that point.
- **Trailing continuation** (inside the last real phase's `runPhaseDp`, `ContinuationSpec`): once the whole list graduates, a real player keeps pulling on that banner, so graduated mass moves into continuation slices that keep pulling with the last phase's 4★ roster, and 4★s on it keep collecting copies past their targets (`continuationLevelCounts`). It runs inside that phase's own DP, rather than as a separate phase seeded from its normalized exit distribution, so copies stay correlated with graduation time — the separate version put 5–10pp errors into the levels above a target. A 4★ off the last roster stays frozen.
- **`sliceResult.ts`'s cache-and-slice**: `useSimulation.ts` caches the largest-budget `SimulationResult` computed for a given (goals, banner-state, CR-settings) key; a pull-budget DECREASE against a matching key is served by truncating the cached arrays, synchronously, with no worker round-trip. See "Known limitations" for the (tiny, accepted) exactness caveat this introduces.
- **Worker lifecycle** (`useSimulation.ts`): the worker runs `runExactSimulation` synchronously on its single thread; a still-in-flight computation that's about to be superseded (by a new input, or by a cache hit) is `terminate()`'d and replaced immediately rather than left to finish a result nobody will use.

## Known limitations — deliberate, measured, not oversights

- **The `crCounter`/persistent-vector time-marginalization residual.** A phase-to-phase handoff (`exitSubstateDist`, normalized, seeding a later same-banner phase's `startDist`) is marginalized over arrival time — correct for the arrival-time distribution itself, but it applies one averaged substate distribution uniformly regardless of when a given trial actually arrives. This is exact when nothing extends a phase past the point where pity/CR naturally resets or stabilizes, but a same-phase anchored 4★ (or any other phase-extending mechanism) breaks that assumption: trials that also fit an intervening detour inside the budget skew toward early-finishing (and therefore atypical-pity-state) trials, so the handoff can systematically over/understate a downstream goal's odds. Measured up to ~8 percentage points in adversarial deep-target-4★-compounding shapes, typically far smaller. **Deliberately left as a known limitation, not fixed**, per explicit user decision — a real fix means re-running a downstream phase separately per arrival-time/state bucket instead of from one merged distribution, a substantial architectural change. See CHANGELOG.md's "twelfth reported bug" entries for the full diagnostic trail if picking this up. **Breakdowns, 2026-09-24:** Monte Carlo breakdowns showed this reaching the constellation/refinement panel in ordinary lists (5–10pp in levels above a target, e.g. one 5★ + her C2 4★: C3 63.8% vs 70.2%). Two targeted fixes removed it for most shapes: the trailing continuation now runs inside the last phase's DP (above), and a 4★ whose window has closed for the rest of her banner has her breakdown taken straight from her last open phase's graduated mass (her copies can't change after it), not through later phases' hand-offs (`frozenAfterByBanner` in `exactEngine.ts`). Those shapes now agree with Monte Carlo within ~0.5pp. What remains is a 4★ still on the roster across several phases of her banner (measured 7.8pp above target for `[O, W, a(→O+M), M]`, 2.3pp for a linked window split by a detour), plus the odds-chart cases above.
- **`sliceResult.ts`'s own small residual.** Slicing a cached larger-budget result is exact only when no banner is reused across phases in a way that makes the requested slice's own implicit "graduated within N pulls" conditioning differ from a fresh N-pull computation's — and this reaches even single-phase goal lists with a 4★ goal, via the trailing-continuation-phase mechanism above (itself a same-banner reuse). Measured worst case ~0.0007 percentage points adversarially — about three orders of magnitude below this app's own display precision. Accepted, applied universally, per explicit user decision (2026-08-21).
- **"Resume the DP on a pull-budget increase" is NOT implemented, and was investigated and rejected, not just deferred.** A "naive resume" design (persist and extend each phase's own DP state, never retroactively refresh a downstream phase's already-fixed `startDist`) was directly measured to introduce a 10-38 percentage point residual in an adversarial (but not extreme) case — 1,000-50,000x larger than the slicing residual above, because a chain of several sequential same-banner phases compounds each hop's own small conditioning error into the next. A second, independent measurement also found `convolve()`'s O(pullBudget²) cost becomes non-negligible for exactly the DP-heavy goal-list shapes resume would help most. Abandoned per explicit user decision (2026-08-21) after a full plan-mode design pass — pull-budget increases remain a full recompute.
- **"Cheap incremental goal-add" is not feasible without deep rework.** `PersistentSpec.dims` is derived from the whole goal list, so adding a goal widens the state-space encoding for every phase of that banner from the start — it isn't an appendable data structure. Same architectural scope as the deferred phase-scoped-`PersistentSpec` limitation below.
- **`PersistentSpec`'s dimensionality is banner-wide, not phase-scoped** — a goal whose value froze after its own phase graduated still rides along as a live dimension in every later phase's state space, which is the root cause of `MAX_TOTAL_FOUR_STAR_GOALS_PER_BANNER`'s low ceiling. Making this phase-scoped instead would be a substantially bigger project than any single fix documented in CHANGELOG.md — not attempted.

## State encoding (`stateCodec.ts`)

Each banner's per-pull state is packed into a single non-negative integer via mixed-radix encoding, so it can key a `Map<number, probability>` (or index a dense array) directly — no object hashing, no decode needed for equality/lookup:

- **Character**: `pity5 (0-89) × guaranteed5 (2) × crCounter (4) × pity4 (0-9) × guaranteed4 (2)`, in that digit order (most-significant first) — `CHAR_BANNER_MODULUS = 90 × 2 × 4 × 10 × 2 = 14,400`.
- **Weapon**: `pity5 (0-76) × guaranteed5 (2) × fatePoints (2) × pity4 (0-9) × guaranteed4 (2)` — `WEAPON_BANNER_MODULUS = 77 × 2 × 2 × 10 × 2 = 6,160`. (A weapon 5★ is certain at pull 77 — measured, despite the in-game text's 80.)

`pity4` is capped at 9 in both transition functions (`characterBanner.ts`/`weaponBanner.ts`) — lossless, since the 4★ rate is flat at 100% beyond pull 9 since the last 4★, but this cap is what keeps the fixed-size encoding valid (uncapped, `pity4` could in principle exceed 9 whenever a run of 5★ pulls takes precedence over 4★ resolution). `pity5` needs no such cap — it's naturally bounded by each banner's own hard pity (90 character / 77 weapon).

The PERSISTENT goal-tracking vector (`goalTracking.ts`'s `PersistentSpec`) uses the same mixed-radix technique (`encodeVector`/`decodeVector`, generic over any `dims` array) but its own `dims` are DERIVED from the goal list, not fixed constants: one `dim=2` slot per distinct `5star_weapon` target id, then one `dim=maxCopies+1` slot per named 4★ goal (`maxCopies` = 7 for character, C0-C6; 5 for weapon, R1-R5). This is why `PersistentSpec` isn't appendable — adding a goal changes `dims` itself (see "Known limitations").

`phaseDp.ts`'s own `exitSubstateDist`/`startDist` keys extend this one level further: `(bannerCode × persistentModulus + persistentCode) × phaseModulus + phaseCode`, always 3-part (`phaseModulus`/`phaseCode` come from `goalTracking.ts`'s `PhaseLocalSpec`, built fresh per phase from whatever `phaseGoals` that specific `runPhaseDp` call was given). Whether a given same-banner reoccurrence preserves the decoded `phaseCode` or resets it to 0 is decided entirely by `exactEngine.ts`, not `phaseDp.ts` itself — see "Window linking"'s FIFO-carry mechanism above.

## Testing strategy

- `exactEngine.test.ts` cross-validates the exact engine against Monte Carlo (`simulate.ts`), series and 4★ breakdowns (the latter on shapes free of the time-marginalization residual) — proves the two *agree*, but a conceptual error shared by both (they're written against the same understanding of the rules) would pass every such test.
- `invariants.test.ts` targets exactly that blind spot: checks logical relationships within the exact engine ALONE (e.g. "a wider anchor window can only help, never hurt") that a shared conceptual bug can't satisfy by construction, since there's no second implementation to (mis)agree with.
- `oddsAudit.test.ts` is a broad, non-pinned cross-validation sweep (deliberately varied combined scenarios — linking + anchoring + cross-phase side-tracking + non-zero starting state + both CR models together) — added specifically to catch what scenario-specific pinned regression tests miss, and has a track record of doing exactly that.
- `trace.ts` / `trace.survey.test.ts` narrate concrete pull-by-pull playthroughs for "why does the engine believe this" — a companion to the numeric checks above, not a replacement.
- `phases.test.ts`, `goalTracking.test.ts`, `goalValidation.test.ts`, `weaponBanner.test.ts`, `characterBanner.test.ts`, `capturingRadiance.test.ts`, `pity.test.ts` — focused unit tests per module.
- `sliceResult.test.ts` — correctness of the pull-budget-decrease cache, including its own known-tiny-residual case.
